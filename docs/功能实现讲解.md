## 1. 环境监测与报警（温湿度 / 燃气 / 烟雾 / 人体 / 门磁）

**原理**：主循环每轮读传感器 → 和阈值比 → 得到 5 个报警位 → 变化时播报 + 上报 + 点灯。

**代码**
- 采集：`device/rk2206_home_safety/home_safety_example.c` 的 `sensor_read_thread` / `body_read_thread`（PIR 单独一个线程，避免 I2C 重试拖慢人体响应）
- 判定：`home_safety_example.c:507-510`
  ```c
  env_alarm = v->temp < cfg.temp_low || v->temp > cfg.temp_high || ...
  bool gas = v->gas_ppm > cfg.gas_limit, smoke = v->gas_ppm > SMOKE_PPM_LIMIT;
  ```
- 传感器驱动：`src/sht30.c`、`src/mq2.c`、`src/bh1750.c`、`src/door.c`、`src/mpu6050.c`
- 状态机与边沿：`src/safety_logic.c:57` `safety_alarm_edges()`（只在 0→1 / 1→0 时触发，不重复报警）

**关键设计**
- 阈值来自**运行时配置**（`cfg.temp_low/temp_high/gas_limit`），不是写死的 `#define` → 现场可下发，不用重烧。
- `include/monitor_logic.h:11` `ENV_LAST_GOOD_MS 6000`：6 秒没读到就标"数据过期"，**避免把旧值当成实时值继续报警或显示正常**。
- 传感器连续失败 3 次后会主动重启 I2C 总线（`src/safety_runtime.c:57` 附近），恢复后 10 秒内不再动，防止抖动。

**可能追问**：「传感器坏了会误报吗？」→ 不会。读失败是 `data_stale=true`，不是"正常"，也不会拿旧值做判定。

## 2. 跌倒检测（板上 IMU）与一键求助

**原理**：三轴加速度合成模长 → 先看失重（<0.6g）→ 1.5 秒内出现冲击（>2.5g）→ 之后 5 秒近乎静止 → 判为疑似跌倒。

**代码**
- 算法：`src/safety_logic.c:12` `safety_fall_sample()`（逐样本状态机）、`:35` `safety_fall_confirm()`（确认与解除）
- 参数：`include/home_safety.h:42-45`（0.6g / 1500ms / 2.5g / 5s）
- 采样：`src/mpu6050.c`，独立线程

**关键设计**
- 三条件串联而不是单看冲击：**单看冲击会把"放下手机/拍桌子"都判成跌倒**。
- 解除条件绑定人体传感器：确认过跌倒后，只有人真的被检测到活动才解除，避免"点一下屏幕就没事了"。
- 求助键（K3）走的是另一条独立链路，**不依赖 IMU**，跌倒检测不可用时（`fall_detection_available=false`）也能呼救。

**可能追问**：「准确率多少 / 误报怎么办？」→ 板上是初筛，App 侧有"疑似跌倒"待处置状态，需要家人确认或有人活动才解除；手表端还有一套更细的判据（见第 11 条）。

## 3. 无活动守护（含睡眠时段、临时暂停）

**原理**：人体传感器多久没触发 → 超阈值报警；睡眠时段内按配置"只记录"或"暂停检测"。

**代码**
- 策略：`src/care_policy.c`（`enabled / sleep / start / end / quiet / noact_ms / revision`）
- 时间窗判定与暂停：`care_policy.c:57` 导出、`:54` `care_policy_pause()`（最长 1440 分钟）
- 下发：`src/cloud_commands.c` 的 `SAFETY_CMD_CARE_POLICY`，App 侧 `pages/CareSettings.ets`

**关键设计**
- **阈值必须落在 10 秒–24 小时**（`src/safety_runtime.c:87-88` 校验），非法值直接拒绝，不会把设备改坏。
- 用 `revision` 做版本号：云端配置和板子本地存储冲突时，取 revision 大的，**避免重启后配置回滚**。
- 时间未同步（`time_synced=false`）时**不进入睡眠时段**——否则时钟错乱会导致整夜不报警。

**可能追问**：「老人睡觉怎么办？」→ 睡眠时段 + `quiet` 选项；这是它存在的唯一原因。

## 4. 自动夜灯（优先级仲裁）

**原理**：光照 < 30 lux 开灯、> 60 lux 关灯（中间死区防抖）；但报警和手动优先级更高。

**代码**：`src/living.c:151`（阈值）、`:162` 一行定优先级
```c
state.light_owner = alarm ? 3 : mask ? 2 : night ? 1 : 0;
```

**关键设计**
- **报警 > 手动 > 自动**：报警时灯必须亮，手动关灯不能灭掉报警灯光（`living.c` 注释与原话：手动关灯不会关闭报警声光）。
- 30/60 之间的死区防止临界光照下灯反复开关。

**可能追问**：「App 里为什么点了开灯又跳回自动？」→ 这是 `light_owner` 仲裁的结果；另有 `config_revision` 防旧配置覆盖。

## 5. 三时段服药提醒（确认 / 撤销）

**原理**：三个时间槽（默认 08:00），到点提醒；老人按键确认后记录 `confirmed_epoch` 与 `dose_day`。

**代码**
- 状态：`src/living.c`（`slots[]`、`medicine_state`、`dose_day`、`confirmed_epoch`、`medicine_revision`）
- 上报字段：`living.c:170` 的 JSON
- App 侧：`pages/Index.ets` 生活提醒卡片（`livingFresh()` / `healthFresh()` 判新鲜度）

**关键设计**
- **`dose_day` 是"哪一天的第几剂"**，不是简单的时间戳比较 → 跨天、断电重启都不会重复提醒或漏提醒。
- `time_synced` 为 false 时不允许确认/撤销：**时间都不准，确认了也没意义**。
- 确认只是"本人/照护者的记录"，页面上明确写了"不等于系统验证实际服药"——**不做过度承诺**。

**可能追问**：「板子和 App 显示不一致？」→ 那是同步问题，不是数据问题：以设备回执为准，App 上"已同步"必须校验 `epoch != 0` 且时间戳新鲜。

## 6. 报警上行链路（板子 → App）

```
传感器 → 报警位 → MQTT(properties/report) → 华为云 IoTDA
      → AMQP 推送 → consume_cloud.py → SQLite → WebSocket → App
```

**代码**
- 上行：`src/mqtt_client.c`（`:414` `next_report = now + cfg.report_ms`）、`src/mqtt_tls.c`
- 消费者：`backend/consume_cloud.py`
- 落库与推送：`backend/backend/app.py`、`backend/backend/store.py`
- App 接收：`services/AlarmNotifications.ets`（WS）+ 启动时补拉 inbox（`models/AlarmInbox.ets`）

**关键设计**
- **上报间隔 `report_ms` 可配（1 秒–1 小时）**，演示时用 1 秒，省电时拉长。
- **WS 只做"实时到达"，落库才是"不丢"**：断线重连后 App 会补拉，避免"当时不在线就永远看不到"。
- 踩过的坑：后端曾用 `(boot_id, up)` 做跨生命周期单调比较，板子 `boot_id` 从 605 变 41 后把健康数据**永久丢弃**；已修。这个坑值得讲——**任何"递增序号"都不能跨重启比较**。

## 8. 本地网页 + NFC（不装 App 也能用）

**原理**：板子自带 HTTP 服务（8080）托管一张网页；NFC 是被动标签，板子每 5 秒把自己的 IP 写进去，手机碰一下 = 浏览器打开这个地址。

**代码**
- 网页：`include/local_page.h`（内嵌 C 字符串）、可读版 `web/index.html`
- 服务：`src/net_server.c`（`:45` 端口、`:94` AP 固定 192.168.2.1、`:657` 任何模式都监听）
- NFC：`src/nfc_tag.c:37` `nfc_tag_set_ipv4()` + `home_safety_example.c:126-139` 的 5 秒线程
- 配对：`src/local_access.c`（`PAIR_TTL 30 分钟`、`REQUEST_TTL 60 秒`、最多 4 个会话）

**关键设计**
- **标签里只有一条 `http://IP:8080/`，不含账号、密码、令牌** —— 路人读走标签也拿不到任何凭据。
- 操作要**板端人工确认**（K5 翻到"手机配对"、K6 同意），授权 30 分钟，板上 K4 可一键撤销全部。
- 写标签**失败不缓存成功状态**，下个周期继续重试；地址没变则不重写，保护标签寿命。

**可能追问**：「碰 NFC 打不开？」→ 标签里是**上次**写进去的地址；板子没联网就不会写新地址。板子离线时碰到的永远是旧 IP。

## 9. 摄像头远程观看（省流 1 秒/帧）

**代码**
- 固件：`device/esp32cam/HomeSafetyCamera/HomeSafetyCamera.ino`（80 口 `/capture` 单张、81 口视频流）
- App：`services/CameraFeed.ets:16` `startPolling(..., intervalMs=1000)`、`pages/Camera.ets`（退避 2→4→8 秒、连续 3 次失败提示检查供电）
- 云端：`backend/backend/camera.py`

**关键设计**
- **81 口是单客户端阻塞的**：一个半开连接能打死整机，所以 App 侧改走 80 口串行轮询，1 秒/帧。
- 曾经用 200ms 轮询（5 帧/秒）→ 40 秒把 ESP32 的 lwIP PCB 池打满，表现像死机。**这个坑是"流畅模式取消"的真实原因**。
- 摄像头上传是"**有人看才传**"（`cloud_upload.h:149` 注释：Idle requests carry only control data，绝不无需求抓图），最多 2 fps。

**可能追问**：「为什么不走视频流？」→ 81 口阻塞风险 + 弱网下整机不可用；省流取图更稳，且演示环境网络不可控。

## 一句话总结（开场白可用）

> 端侧负责"感知 + 本地兜底"，云侧负责"汇聚 + 触达"，近场（NFC / 局域网）负责"断网也能用"。三层各自能在上一层失效时独立工作，这是这套系统最核心的设计取舍。
