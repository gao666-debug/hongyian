## 一、⚠️ 先说冲突：PB5 可能不干净

队友定的引脚是 **`GPIO0_PB5`**。但我核查通晓源码与原理图后，发现这个脚**很可能不是空闲脚**。

### 证据一：代码层面（确凿）

通晓官方**三个**案例都把板载 RGB **红灯**定义在 PB5，并且是配成**输出**用于报警点灯：

| 文件 | 定义 |
|---|---|
| `e1_iot_smart_home_hwiot/src/drv_light.c:4` | `#define LED_R_GPIO_HANDLE GPIO0_PB5` |
| `e1_iot_smart_home/src/drv_light.c:4` | 同上 |
| `d1_smart_home/src/smart_home.c:31` | 同上 |

且随后执行：

```c
IoTGpioSetDir(LED_R_GPIO_HANDLE, IOT_GPIO_DIR_OUT);
IoTGpioSetOutputVal(LED_R_GPIO_HANDLE, IOT_GPIO_VALUE1);   // 点亮红灯
```

> `e1_iot_smart_home_hwiot` 正是本项目南向固件的基线案例。

### 证据二：硬件层面（未确证，需目视核对）

原理图里 RGB 灯有**独立网络名**：`RED_LED` / `GREEN_LED` / `BUE_LED` / `STATE_LED`。
但对原理图 PDF 做全文检索，**`B5` 与 `LED` 从未出现在同一行**——因为网标与走线是分开的绘图元素，
文字层无法证明 `PB5` 与 `RED_LED` 是否同一条网络。

**确定的事实**：PB5 确实引到了 E53 接口，网络名 **`E53_PWM1_M1_GPIO_B5`**。

### 结论与风险

**PB5 极可能是"板载红灯驱动脚 + E53 引出脚"的双重身份引脚**（E53 的 PWM 脚与板载 RGB 共用，这在轻量开发板上很常见）。

若确认同网，风险有三：

| # | 风险 | 后果 |
|---|---|---|
| 1 | 固件若仍把 PB5 配成**输出** | 与接收模块输出**推挽对撞** → 读不到按键，严重时损伤一方驱动级 |
| 2 | 固件配成**输入**，但 LED 电路仍挂在该线 | 若 LED 直接接在脚上，电平会被**钳在 LED 正向压降（约 2V）**，可能达不到逻辑高阈值 |
| 3 | 红灯被占用 | 报警时**少一个红色** —— 红光是最重要的报警色 |

### 请队友确认的三件事

1. 当前固件里，**PB5 是否已完全不再配成输出**？（RGB 红灯是否还用它、或已改用别的脚）
2. 原理图上 **PB5 是否直连 RED_LED**？（打开原理图 LED 那页目视核对，最直接）
3. 若确认共用 → 是否改用 **`E53_GPIO_A2`（GPIO0_PA2）**？这是经源码全量核查后**唯一真正空闲**的脚。

> 实测验证法：把 PB5 配成输入，从外部给 3.3V 高电平，**观察红灯是否亮**。
> 亮 → 说明 LED 挂在这条线上，不能当输入用。

### 附：我已核查过的引脚占用（供参考）

| 引脚 | 占用者 |
|---|---|
| PA0 / PA1 | I2C0（SHT30 温湿度 + BH1750 光照）|
| PA3 | 人体红外 |
| PA4 | LCD 的 DC 线 |
| **PA5** | 报警灯 / LED（`b1_gpio` 用的就是 PA5）|
| **PB4 / PB5 / PD0** | **RGB 三色灯** |
| PC0~PC3 | LCD SPI（CS/CLK/MOSI/RES）|
| PC0 / PC5 | ADC（可燃气体等）|
| PC7 | 按键 |
| B2 / B3 | 语音模块串口（UART2）|
| **PA2** | **未发现任何占用** ← 唯一干净的脚 |

## 二、采购规格（按队友固件要求收窄）

| 项 | 要求 | 说明 |
|---|---|---|
| **输出模式** | **点动（momentary / jog）** | 空闲低 → 按下高 → 松开恢复低。**禁用自锁、禁用翻转** |
| **极性** | **高电平有效** | 固件检测"低→高"变化 |
| **输出持续时间** | **必须 > 300 ms** | 固件约 300ms 轮询一次；短脉冲会漏检 |
| **供电** | **3.3 V** | ⚠️ 不要 5V |
| **输出电平** | **3.3V CMOS**（跟随供电电压） | 与 RK2206 的 3.3V IO 匹配 |
| **共地** | 与开发板共地 | 必须 |
| 编码类型 | EV1527 / PT2262 学习码 | 便于配对，无需焊接编码电阻 |
| 接收灵敏度 | ≤ -105 dBm 更佳 | 家用穿墙够用 |

## 三、⭐ 一个关键建议：优先找"延时输出模式"的模块

**问题**：点动模式下，输出高电平**持续时间 = 老人按住按钮的时间**。
正常人点击约 **100–200 ms** —— **小于固件的 300 ms 轮询周期 → 有漏检风险！**

**建议**：选支持**「延时输出」模式**的接收模块 —— 按一次输出**固定时长**（如 5 秒）高电平，然后自动恢复低。

为什么这个模式最合适：

| 要求 | 是否满足 |
|---|---|
| 持续时间 > 300ms | ✅ 固定 5 秒，绝对够 |
| 不锁存（松开恢复低） | ✅ 5 秒后自动恢复低，非锁存 |
| 持续高只触发一次 | ✅ 固件是边沿触发，只算一次 |
| 允许重复求助 | ✅ 5 秒后自动恢复，可再次触发 |

> 市面部分接收模块支持"点动 / 自锁 / 互锁 / 延时 5s / 10s / 15s / 20s"多种模式，
> **下单时务必确认是否含延时模式**。

**另一条路**：队友提到"后续会完善快速采样和消抖"。
若改成**边沿中断**（而非轮询），则不再受 300ms 限制，普通点动模式即可。
**两种方案二选一，建议和队友对一下哪个先落地。**

## 五、接线（3 根线）

| 接收模块引脚 | 接到 |
|---|---|
| **VCC** | **3.3V** ⚠️ 不要接 5V |
| **GND** | GND（与开发板共地）|
| **OUT**（数据输出，如 D0） | 固件指定引脚（**待确认**，见第一节）|
| ANT | 焊一根 **17 cm 导线**当天线 |

> **天线别省**：不接天线只能覆盖十几米，接了能到 50–100 米。

## 六、下单前问卖家的问题清单

直接复制问客服：

1. 接收模块支持**点动模式**吗？输出是不是"按下高、松开低"？
2. **输出高电平持续时间**是多少？能不能做到 **1 秒以上**？
3. 有没有**延时输出模式**（按一次输出固定时长后自动恢复）？
4. 模块 **3.3V 供电**时，输出高电平是多少伏？（必须是 3.3V）
5. 支持 **EV1527** 编码的遥控器吗？配套遥控器是哪个型号？
6. 遥控器电池是什么规格？能换吗？

## 七、配套建议（与按钮同等重要）

### 7.1 加"已收到"反馈 —— 把单向盲发变成可确认

433MHz 是**单向**的：老人按下去，**他不知道信号有没有发出去**。紧急时刻这个不确定性很要命。

做法：板子收到按键后，让语音模块播报一句
**"已收到求助，正在联系家人"**。

SU-03T 板载现成，软件加一行调用即可。这一下就把"盲发"变成了"可确认"。

### 7.2 语音呼救作为第二通道

按钮有个硬伤：**老人可能摔在离按钮远的地方，或按钮被压在身下够不着**。
而喊"救命"是本能反应，不需要摸到任何东西。

板载 SU-03T 支持离线唤醒，配个命令词即可，**零硬件成本**。

**两个通道都做**，可靠性才够，也是答辩能讲的设计点：
> "我们设计了双重呼救通道，按键与语音互为备份。"
