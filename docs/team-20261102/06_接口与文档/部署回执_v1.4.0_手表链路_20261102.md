### 与仓库版本的三处刻意偏差

**① 手表数据挂「主设备」，但不是直接拿 `settings.device_id`**

仓库原码：`device = settings.device_id`。
本项目 `settings.device_id` 是**逗号分隔的多设备字符串**，照搬会把手表数据写到
`device="6acd...,6ae6..."` 这种脏键上。改用 `settings.primary_device`（= `device_ids[0]`），
语义与仓库一致（数据挂 App 面向的那台），但不会写出脏键。

**② 白名单拆成两层**

- `device_ids` = App 可见设备（主板 + 环境节点，**手表不在内**）
- `allowed_device_ids` = `device_ids` + 手表（供入库校验）

这样登录下发的仍是 2 个设备 ID（前端不用新增第三张卡），
但手表的消息不会被消费者或 `check_device` 拒掉。

**③ 非手表设备的属性上报返回 200-ignored**

WS63 环境节点每 10 秒也发属性上报，服务 ID 同样是 `11`。
若照仓库逻辑一律送进 `ingest_watch`，会因「无手表属性」被 422 → 每 10 秒一条死信。
现在：未知设备 404；已知但非手表 → 200 + `{"ignored": true}`，不进死信。

## 六、✅ 核实结论：手表节点 ID 不用改（原判断已更正）

### 原先的判断

部署时发现 IoTDA 上手表设备是这样的：

```
device_id = demo-watch
node_id   = DEVICE_ID          ← 看起来像忘记改的示例文本
```

当时判断「需要把节点 ID 改成真实 SN」，并准备了一套四步操作。
**这个判断是错的**，2026-11-02 15:58 核实后更正。

### 实际证据：它成功上报过真实数据

查手表设备影子，里面有真实测量值（不是示例数据）：

```
service_id='11'   event_time=2026-11-01T034402Z  （本地 11:44）
heart_rate=100  spo2=99  accel_x=-61  accel_y=-330  accel_z=920  steps=11  fall_state=0
```

对比 `service_id='Health'`（11-01 10:41）里的 `72/98/1234`——那才是手册里的示例值，
说明 `11` 这条是**设备真实跑出来的**。

⇒ 云端 device_id、设备密钥、固件 `HY_HW_DEVICE_ID`、转发规则 SQL **全都对得上**，
设备曾经正常接入并上报。现在 OFFLINE 只是没开机/没联网。

### 为什么不该改

`_DEVICE_ID` 的来源是固件模板 `device/203_watch/src/hy_cloud_cfg.example.h`：

```c
#define HY_HW_DEVICE_ID   "xxxxxxxxxxxxxxxxxxxxxxxx_DEVICE_ID"
```

注册时把示例文本原样填了，**名字难看但语义正确**。改名的连锁代价：

| 步骤 | 影响 |
|---|---|
| 华为云删设备重注册 | 设备密钥重置，旧密钥作废 |
| 固件改 `HY_HW_DEVICE_ID` + 密钥 | **必须重新烧录** |
| 服务器 `.env` 改 `WATCH_DEVICE_ID` | 需重启 api + amqp |
| 转发规则 SQL（截图那条 `12345`） | `WHERE device_id = '...'` 必须同步改，漏了就断链 |

而华为云的「修改设备」接口**只支持改**
`device_name` / `description` / `extension_info` / `auth_info`（SDK `UpdateDevice` 字段已确认），
**没有 `node_id`**，所以想改只能走「删除重注册」这条重路。

> 结论：**保持现状**。想让界面好看只改 `device_name`（如「203手表」）。

### 附带发现：影子里有两个服务 ID

`Health`（11-01 10:41，示例值）与 `11`（11-01 11:44，真实值）并存。
后端 `pick_service()` 先认 `WATCH_SERVICE_ID=11`，找不到再按属性特征回退，
**两种都能正确处理**，不需要清理。
