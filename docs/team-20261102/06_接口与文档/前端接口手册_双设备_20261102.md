| # | 改什么 | 为什么 | 严重度 |
|---|---|---|---|
| 1 | `Backend.device` 从单值改成按登录返回的 `device_ids` 选择 | 登录响应现在返回 **两个** 设备 ID，代码里 `device='demo-device'` 的硬编码必须换掉 | 🔴 阻塞 |

## 1. 三块硬件分别是什么

| | **主监护板** | **环境节点（星闪）** | **手表（穿戴）** |
|---|---|---|---|
| 设备 ID | `demo-device` | `demo-environment` | `6ae6a5c1e094d615927efdbd_…`（节点 ID 待确认） |
| 硬件 | 通晓 TX-SMART-R / RK2206 | WS63 星闪开发板 | WS63 + 1.28″ 圆屏 + MPU6050 + MAX3010x |
| 固件（实测） | `v3.5.42` | `ws63-home-1.0` | `203_watch` |
| 华为云产品 | 产品 `11`，服务 `HomeSafety` | 产品 `33`，服务 ID `11` | 产品 `22`，服务 ID `11` |
| 上报通路 | MQTT 消息 → IoTDA → AMQP → 后端 | 同左 | MQTT **属性上报** → IoTDA → AMQP → 后端 |
| 上报类型 | `device_health`、`activity_stats`、`alarm_event` | **只有 `device_health`** | **只有 `device.property`** |
| 上报频率 | health 约 60 秒 | **10 秒**，门磁/人体变化时立即补发 | **10 秒** |

> `/devices/{主监护板}/watch` 读取。原因见 §5.10。

## 2. 通用约定

| 项 | 值 |
|---|---|
| Base URL | `https://SERVER_IP:8443`（自签证书，App 需内置 `development-ca.crt`） |
| 协议 | HTTPS / WSS，**不接受 http** |
| 鉴权 | `Authorization: Bearer <access_token>` |
| 令牌有效期 | 28800 秒（8 小时） |
| 响应信封 | 见下 |
| 时间戳 | 除特别说明外都是 **Unix 秒**（不是毫秒） |

### 统一响应信封

```json
{
  "code": 0,
  "message": "ok",
  "data": { },
  "request_id": "8df6c042b10f464b8e3e257d3610c270",
  "mode": "live",
  "simulated": false
}
```

- `code != 0` 即业务失败，`message` 可直接展示（中文）
- HTTP 401 = 令牌失效，需要重新登录
- 所有 `data` 都可能为 `null`，**解析前必须判空**

### 错误码速查

| HTTP | 含义 | 前端处理 |
|---|---|---|
| 401 | 未登录 / 令牌过期 | 跳登录页 |
| 404 | 设备 ID 不在白名单 | 检查是否用了未配置的设备号 |
| 422 | 参数校验失败 | 检查请求体字段 |
| 429 | 登录尝试过多（60 秒 10 次） | 提示稍后重试 |
| 502 | 华为云 IoTDA 不可用 | 提示「云端暂不可用」，可重试 |

404 的真实返回长这样（设备 ID 不在白名单时）：

```json
{ "code": 404, "message": "Device not configured", "data": null,
  "request_id": "45106b7636bd4d7f843efb290543db6d", "mode": "live", "simulated": false }
```

## 3. 登录与设备发现

### `POST /api/v1/auth/login`

**请求**

```json
{ "username": "guardian", "password": "******" }
```

**真实响应**

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "access_token": "<TOKEN>",
    "token_type": "Bearer",
    "expires_in": 28800,
    "username": "guardian",
    "device_ids": [
      "demo-device",
      "demo-environment"
    ]
  },
  "request_id": "...",
  "mode": "live",
  "simulated": false
}
```

> ⚠️ **这是本次最重要的变化**：`data.device_ids` 从「只有 1 个」变成「可能有多个」。
> 现有 `Models.ets` 的 `LoginData` 只有 `access_token`，**把 `device_ids` 解析丢掉的话，前端永远只能看到一台设备**。

### `POST /api/v1/auth/logout`

无请求体，返回 `{"data": {"logged_out": true}}`。

### 设备名称

后端**没有**设备名称、型号、房间号这类元数据接口。设备 ID 是 `{产品ID}_{节点ID}` 格式，节点 ID 可作简短显示名（如 `TXSMART001` / `1234`）。要友好的名字只能前端本地做映射。


**新设备真实响应（后端 1.3.1 修复后，2026-11-02 13:46 实测）**

```json
{
  "code": 0,
  "data": {
    "device_id": "demo-environment",
    "service_id": "11",
    "online": false,
    "updated_at": "2026-11-01T10:50:05Z",
```

> ✅ 1.3.1 之前这里返回的是 `properties: {}`、`updated_at: null`（后端只认 `HomeSafety` 服务，
> 而 WS63 的属性挂在服务 `11` 下）。现已修复，两台设备都能正常取到属性。改动详情见 §8.1。
> ⚠️ 两台设备 `online` 都是 `false`，即使旧设备当时正在实时上报 —— **这个字段不可信**。

`properties` 字段语义（**两台设备的 `light` 含义完全不同**）：

| 字段 | 旧设备 | 新设备 | 说明 |
|---|---|---|---|
| `temp` / `humi` | 有 | 无 | ℃ / %RH |
| `gas` | 有 | 无 | 燃气 ADC |
| `light` | **百分比 0~100** | **ADC 电压 mV 0~3300** | 🚨 同名不同义，不能共用一套渲染 |
| `smoke` | 0/1 布尔 | **ADC 电压 mV 0~3300** | 🚨 同上 |
| `body` | 0/1 | 0/1 | 人体感应，一致 |
| `door` | **0/1 数字** | **"OPEN"/"CLOSED" 字符串** | 🚨 类型不同 |
| `inactive` / `alarm` / `status` / `help` / `fall` / `gas_alarm` | 有 | 无 | 主监护板专有 |

### 5.3 `GET /devices/{id}/alarms?limit=50&offset=0`

`limit` 1~100，`offset` ≥0。**新设备返回空数组。**

**旧设备真实响应（实测，原样截取 2 条）**

```json
{
  "code": 0,
  "data": {
    "items": [
      { "key": "554:335", "schema": 1, "boot_id": 554, "event_id": 335,
        "code": 1, "value": 0.0, "phase": "end", "duration": 2,
        "epoch": 1793550390, "up": 63, "message_id": "554-335-1-4" },
      { "key": "554:334", "schema": 1, "boot_id": 554, "event_id": 334,
        "code": 3, "value": 794.0, "phase": "end", "duration": 8,
        "epoch": 0, "up": 15, "message_id": "554-334-1-2" }
    ],
    "limit": 2,
    "offset": 0
  }
}
```

- 服务端**已经返回好了 `key` 字段**（格式 `boot_id:event_id`），备注接口直接用 `item.key`，不用自己拼
- `phase`：`start` / `end` / `record`
- `code` 对照（前端 `alarmTitle()` 已有映射）：`0` 正常 / `1` 紧急求助 / `2` 疑似跌倒 / `3` 燃气异常 / `4` 活动异常 / `5` 温湿度异常
- **`epoch` 可能是 `0`**（上面第二条就是，设备当时未校时）—— 这时要用 `up`（开机秒数）显示相对时间，别渲染成 1970 年

**新设备**

```json
{ "code": 0, "data": { "items": [], "limit": 50, "offset": 0 } }
```

### 5.7 `POST /api/v1/commands` —— 仅旧设备

> ⚠️ 本节响应结构**依据后端实现整理**（`app.py` 的 `command_data()`），本次**未向真机下发命令**，
> 以免干扰正在运行的设备。联调时请以实际返回为准。

```json
{
  "device_id": "demo-device",
  "service_id": "HomeSafety",
  "command_name": "ack",
  "paras": {},
  "client_request_id": "<uuid>"
}
```

- 返回 **202** + `{"command_id": "...", "state": "pending"}`
- 轮询 `GET /api/v1/commands/{command_id}`，`state`：`pending` / `executed` / `failed` / `unknown`
- `unknown` = 网络超时，**无法确定设备是否执行**，UI 应提示"状态未知"而不是"失败"
- 支持的 `command_name`：`ack`、`mute`、`set_living`、`confirm_medicine`、`set_medicine_plan`、`set_medicine_state`
- ⚠️ **新设备不要调用**：WS63 固件没有命令处理，后端会走 IoTDA 同步命令并超时（返回 `unknown`），白白等 15 秒

### 5.9 实时推送（WebSocket）

**第一步：换票** `POST /api/v1/ws-ticket?device_id={id}`

```json
{ "code": 0, "data": { "ticket": "<一次性票据>", "expires_in": 30,
                       "path": "/api/v1/ws", "device_id": "demo-device" } }
```

**第二步：连接** `wss://SERVER_IP:8443/api/v1/ws?device_id={id}&ticket={ticket}`

- 票据**一次性**、30 秒过期，每次重连都要重新换票
- 连接建立后先收到 `hello` 帧
- 每 15 秒收一次 `ping`，**必须回 `pong`**，否则会被断开
- 服务端队列溢出会推 `resync_required`，收到后应断开重连并全量刷新

**推送帧格式**

```json
{ "schema": 1, "type": "health", "device_id": "...", "timestamp": "2026-11-02T05:40:00Z",
  "mode": "live", "simulated": false, "data": { } }
```

| `type` | `data` 内容 | 触发 |
|---|---|---|
| `hello` | 无 | 连接建立 |
| `ping` | 无 | 保活（需回 pong） |
| `health` | 与 §5.2 的 `data` 同构 | 设备上报健康 |
| `alarm` | 单条报警事件 | 设备报警 |
| `stats` | 与 §5.5 `latest` 同构 | 活动统计 |
| `command_ack` | 命令结果 | 命令状态变化 |
| `capture` | 抓拍元数据 | 新抓拍入库 |
| `resync_required` | 无 | 需重连全量刷新 |

> ⚠️ **一条 WS 连接只对应一台设备**（`device_id` 是查询参数）。要两台设备都实时，
> 需要**两条连接**（或只连当前查看的那台，另一台靠轮询）。

## 5.10 手表（WS63 穿戴节点）—— 2026-11-02 新增

### 先理解一个关键设计：手表不是「第三台设备」

系统里有 **3 块硬件**（主监护板、环境节点、手表），但 App 只看到 **2 台设备**：

- 手表是「人」身上的穿戴设备，**数据挂载在主设备下**（`device_ids[0]`）
- 所以 `login` 返回的 `device_ids` 仍然是 **2 个**，手表**不会**作为第三个 ID 出现
- 取手表数据用 **主设备的 ID**，路径是 `/devices/{主设备}/watch`

> 这样设计的好处：App 不用维护"这台设备是主板还是手表"的分支，
> 「主板 + 手表 = 一个被监护的人」，语义更自然。

### 5.10.1 `GET /devices/{device}/watch` —— 最新一帧

**真实响应**（我用注入数据实测的，结构就是固件上报后归一化的结果）

> 前端应当把 404 当作"暂无手表数据"处理，而不是弹错误。

**字段说明**

| 字段 | 类型 | 说明 |
|---|---|---|
| `heart_rate` | int | 心率 bpm。**为 0 表示这次没测到**（手指没贴上），不是"心率 0" |
| `hr_measuring` | bool | 上面那个 0 的判定结果。**画曲线/做告警前先看它**，为 false 就别画 |
| `spo2` | int | 血氧 %，0 同样表示未测到 |

| `accel_g` | object | 同一数据的 **g** 单位版本，直接用这个显示更直观 |
| `motion_mg` | int | 合加速度模长 `√(x²+y²+z²)`，静止约 1000 |
| `dynamic_mg` | int | `abs(motion_mg - 1000)`，扣掉重力后的动态分量。**看走路/抖动用这个**，比单轴直观 |
| `posture` | string | `z_up` / `x_up` / `y_up` / `moving`，粗姿态，**仅供参考，不能当跌倒结论** |
| `steps` | int | 上电以来累计步数，重启归零 |
| `fall_state` | int | **此刻状态**：0 正常 / 1 冲击后观察中 / 2 疑似摔倒 |
| `fall_count` | int | 上电以来累计摔倒次数，重启归零 |
| `fall_active` | bool | `fall_state == 2`，方便你直接绑 UI |
| `fall_watch` | bool | `fall_state == 1`（观察中） |

> 🚨 `fall_state` 和 `fall_count` **不能互相替代**：前者是"现在摔没摔"，后者是"今天摔了几次"。
> 另外 `fall_count` 重启会归零，**不要用它做历史统计**，历史看下面的跌倒事件接口。

## 7. 字段陷阱清单（照着核对，能省半天）

1. **`light` 同名不同义**：旧设备是百分比 0~100，新设备是 ADC 电压 mV 0~3300。混用会显示成 50700%。
2. **`smoke` 同理**：旧设备 0/1 布尔，新设备 mV。
3. **`door` 类型不一致**：数字 `1` vs 字符串 `"OPEN"`。判断开门请写
   `const isOpen = typeof door === 'string' ? door === 'OPEN' : door === 1;`
4. **大量字段为 `null`**：新设备 `living`、`door_valid`、`data_state`、`time_synced` 都是 null；
   旧设备的 `light/smoke/body/door` 也是 null。判空不能省。
5. **时间戳是 Unix 秒**，`new Date(x * 1000)`，别直接塞给 `new Date(x)`。
6. **`epoch` 可能为 0**（设备未校时），此时只能用 `up`（开机秒数）显示相对时间。
7. **`shadow.online` 不可信**，两台设备都返回 false。
8. **WS 一条连接只服务一台设备**，别指望一个 socket 拿两台的数据。
9. **`/captures/{id}` 返回二进制**，不是 JSON，必须设 `ARRAY_BUFFER`。
10. **`device_ids` 可能只有一台**（如果线上只配了一台），不要写死索引 `[1]`。
11. **`heart_rate: 0` 不是"心率 0"**，是这次没测到（手指没贴上）。画曲线/报警前先看 `hr_measuring`。
12. **`fall_count` 重启会归零**，不能拿它做历史统计；历史看 `/watch/falls`。
13. **`/watch` 返回 404 是正常状态**（还没有任何手表上报），不要当错误弹窗。
14. **`/watch` 系列要用主设备 ID**，传手表 ID 虽然不会被拒，但读到的还是主设备下的数据。

### 8.1 ✅ 新设备 `/shadow` 为空 —— 已于 2026-11-02 修复（API 1.3.1）

**原来是什么样**：新设备 `/shadow` 返回 `properties: {}`、`updated_at: null`，前端按老逻辑读会整屏空白。

**根因**：`backend/cloud.py` 写死了服务 ID 过滤 ——
`next((s for s in raw['shadow'] if s.get('service_id')=='HomeSafety'), {})`。
而 WS63 的属性挂在**服务 `11`** 下，明明有数据却被过滤掉（直连 IoTDA 可查到
`light=507 smoke=159 body=1 door=OPEN`）。

**怎么修的**（`cloud.py` 的 `shadow()`）：

- 有 `HomeSafety` 服务且有属性 → 只取它（**主监护板行为逐字节不变**）
- 没有 → 合并所有服务的 `reported.properties`（新设备走这条）
- `updated_at` 与属性**取自同一个服务**，避免「旧属性配新时间」
- `service_id` 返回真实命中的服务（旧设备 `HomeSafety`，新设备 `11`）

```json
               "online": true, "last_seen": 1793551913, "fw": "v3.5.42" } ] }
```

有了它，前端就不用靠设备 ID 前缀猜型号。

### 8.4 🟡 新设备不上报报警与统计

WS63 有烟雾、门磁、人体传感器，但固件**只上报 health 快照**，不产生 `alarm_event`，
也不上报 `activity_stats`。所以新设备的「报警」和「趋势」在数据层面就是空的。

**要变成真报警**，需要固件侧：烟雾超阈值、门磁开启超时、长时间无活动时补发 `alarm_event`。
这是固件工作，不是前端能解决的。

### 8.5 🟡 新设备不支持命令下发

WS63 固件没有订阅命令 Topic，`POST /commands` 会走 IoTDA 同步命令并超时。
前端对新设备**不要渲染任何命令按钮**。

### 8.6 ✅ AMQP 通道曾中断约 5 分钟，已于 13:50 修复

**这条现在只是背景知识**：如果你在 2026-11-02 13:45–13:50 之间看到数据不更新，是这个原因，不是接口坏了。

现象：`eldercare-amqp` 服务显示 `active`，但日志每 5 秒刷
`[cloud-consumer] Transport failure; reconnecting`。

根因：**华为云 AMQP 接入凭证过期**。这类故障很隐蔽 —— 凭证过期后已建立的连接不会被踢掉，
所以平时毫无异常，只有重启服务重新建连时才暴露。

已通过重新生成接入凭证修复，13:50:21 日志出现 `AMQP connected`，之后稳定。

> **对前端的实用意义**：判断"数据是不是新的"，不要看接口有没有报错（永远 200），
> 要看 `shadow.updated_at` 是否在变。设备离线或链路中断时，接口一样返回 200，只是值是旧的。

## 10. 排障速查

| 现象 | 多半是 | 怎么确认 |
|---|---|---|
| 新设备界面全空 | 读了 shadow（§8.1） | 直接看 `/shadow` 的 `properties` 是否 `{}` |
| 新设备显示离线但其实在传 | 用了 `shadow.online` | 看 `/health` 的 `epoch` 是否在变 |
| 404 Device not configured | 设备 ID 不在 `.env` 的 `DEVICE_ID` 白名单 | 登录返回的 `device_ids` 里有没有它 |
| 502 | 华为云 IoTDA 不通 | 看服务器 `journalctl --user -u eldercare-api` |
| WS 连上就断 | 没回 `pong` 或票据过期 | 抓 `ping` 帧，确认 15 秒内回了 `pong` |
| 数值明显不对（如 50700%） | `light`/`smoke` 单位混用 | 按固件区分：WS63 是 mV |
| 抓拍取图解析失败 | 把二进制当 JSON 解了 | 改 `expectDataType: ARRAY_BUFFER` |
