## 一、为什么要改

新增第二台设备（WS63 星闪环境节点 `demo-environment`）后，
它的 `GET /shadow` 返回 `properties: {}`、`updated_at: null`、`online: false`——空壳。

App 的实时数据**全部**来自 `shadow.properties`（`Index.ets` 的 `refresh()`），
所以前端接上新设备会**整屏空白**。

### 根因是后端过滤写死，不是设备没上报

`backend/cloud.py` 原来的 `shadow()`：

```python
service = next((s for s in raw.get('shadow',[]) if s.get('service_id')=='HomeSafety'),{})
```

只认 `HomeSafety` 服务。而 **WS63 的属性挂在服务 ID `11` 下**（华为云产品 `33` 的物模型）。
直连 IoTDA 查原始影子，数据是完整存在的：

```
service_id='11'   light=507  smoke=159  body=1  door=OPEN   event_time=20261101T105005Z
```

对比旧设备：

```
service_id='HomeSafety'   13 个属性（temp/humi/gas/light/body/inactive/alarm/status/help/fall/gas_alarm/smoke/door）
```

两台设备的物模型服务 ID 不同，旧代码只认一个，所以新设备被过滤成空对象。

## 二、改了什么

只改 `backend/cloud.py` 的 `shadow()`，外加 `app.py` 的版本号。**没有动数据库、`.env`、nginx、systemd。**

新逻辑：

1. 有 `HomeSafety` 服务**且有属性** → 只取它 ⇒ **主监护板行为逐字节不变**
2. 没有 → 合并所有服务的 `reported.properties` ⇒ 新设备能取到 4 个属性
3. `updated_at` 与属性**取自同一个服务**（第一版曾取全局最新时间，会出现「旧属性配新时间」，已修正）
4. `service_id` 返回真实命中的服务（旧设备 `HomeSafety`，新设备 `11`）

```python
preferred = next((s for s in services
                  if s.get('service_id') == 'HomeSafety' and reported_props(s)), None)
if preferred is not None:
    chosen = preferred
    properties = dict(reported_props(preferred))
    stamp = (preferred.get('reported') or {}).get('event_time')   # 同源
else:
    chosen = next((s for s in services if reported_props(s)), {})
    properties = {}
    for service in services:
        properties.update(reported_props(service))
    stamps = [...有属性服务的 event_time...]
    stamp = max(stamps) if stamps else None                        # 合并模式取最新
```

> 为什么保留 `HomeSafety` 优先而不是无条件合并：现场只有两台设备、各一个服务，
> 但若将来主监护板新增服务，无条件合并会让新服务的同名属性覆盖主板的，
> 优先 `HomeSafety` 能保证主监护板语义永远不变。

## 四、✅ 部署时暴露的另一个问题：AMQP 接入凭证失效（已修复）

**这不是本次改动引起的，但被这次重启暴露出来。**

重启 `eldercare-amqp` 后，它每 5 秒报 `Transport failure; reconnecting`，无法连上华为云。

排查过程：

| 检查 | 结果 | 结论 |
|---|---|---|
| TCP 到 `:5671` | 可达 | 网络没问题 |
| `openssl s_client` TLS 握手 | `CONNECTION ESTABLISHED`，证书验证 OK，有效期至 2026-12-28 | TLS 没问题 |
| HTTPS 接口（shadow/health） | 全部正常 | AK/SK、实例、网络都正常 |
| 正确凭证 vs 故意错误密码 | 两者**表现完全相同**：`amqp:connection:framing-error / connection aborted` | 服务端对认证失败统一 abort ⇒ **凭证失效** |

**根因**：`AMQP_ACCESS_KEY` / `AMQP_ACCESS_CODE` 过期。

**为什么之前一直"正常"**：`.env` 是 2026-10-17 生成的，10-24 重启时还能连上，之后连接一直保持没断过。
凭证过期后，**已建立的连接不会被踢掉**，所以没有任何报错；只有重新建连（重启服务）才会暴露。

### 修复过程

1. 备份 `.env` → `.env.bak-20261102-135015`
2. 用现有 AK/SK 调 IoTDA `CreateAccessCode`（`type=AMQP`、`force_disconnect=True`）生成新凭证
3. 原子替换 `.env` 的 `AMQP_ACCESS_KEY` / `AMQP_ACCESS_CODE`，`chmod 600`，回读校验一致
4. `systemctl --user restart eldercare-amqp.service`

### 修复结果

```
2026-11-02T13:50:21  Started Eldercare AMQP Cloud Consumer.
2026-11-02T13:50:21  [cloud-consumer] AMQP connected
```

之后 **60 秒无任何重连报错**，连接稳定。

> `inbox` 计数暂时没涨，是因为两台设备此刻都不在线上报（最后分别为 11-02 00:51 / 11-01 18:50），
> 不是链路问题。设备下次上线即可正常入库。

**脚本**：`patches_20261102/rotate_amqp_credential.py`（备份 → 生成 → 原子替换 → 回读校验，凭证输出已脱敏）

### ⚠️ 注意事项

- 这套接入凭证如果仍按短期有效期发放，**将来还会以同样方式静默失效**。
  建议在华为云 IoTDA 控制台把接入凭证设为长期有效，或定期主动轮换。
- 惰性故障的特征是"一直好用，一重启就全挂"。以后**每次重启 AMQP 后都要确认日志出现
  `Device message persisted`**，不要只看 `systemctl is-active`（它一直显示 active）。
- `consume_cloud.py` 的 `on_transport_error` 只打一行通用日志。本次是靠临时脚本打印
  `event.transport.condition` 才定位到 framing-error。建议后续把它加进正式日志。
