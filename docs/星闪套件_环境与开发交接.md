## 4. 建议的环境搭建顺序

### 4.1 先锁定版本和安装路线

首选向套件提供方取得与 2025-04/05 教程匹配的完整 SDK、工具链或有效镜像及校验值，先跑通随板示例。

若旧镜像无法取得，再参考官方固定版本路线：

- 官方指南仓库：<https://gitee.com/HiSpark/ohos_ws63>
- 官方 SDK 仓库：<https://gitee.com/HiSpark/fbb_ws63>
- 官方文档：<https://docs.hisilicon.com/repos/fbb_ws63/zh-CN/master/>
- 官方指南中的 WSL 包：<https://hispark-obs.obs.cn-east-3.myhuaweicloud.com/fbb_ws63_wsl.tar>（本次 HEAD 返回约 1.7GB；环境包不应假定包含全部项目源码）

官方新教程中列举的润和/其他板卡与本项目软通教育套件并非同一板型。可以参考工具链、构建流程，**不能直接照搬其他板子的 GPIO、外设初始化或成品固件**。`fbb_ws63` 的当前 SDK 与套件旧示例也要验证 API 兼容性。

### 4.2 电脑侧准备

- Windows + WSL2（或 Ubuntu 虚拟机），无需两套板分别安装两个系统。
- VS Code 用于编辑；Docker 不是唯一选择，也可以用厂商支持的独立 Linux/HiSparkStudio 环境。
- 独立源码目录，例如 `~/nearlink/ws63_ohos`，避免与 RK2206 工程混合。
- 按所选版本文档安装 Python、CMake、Ninja、git-lfs、repo 及 RISC-V 交叉工具链；版本以实际 SDK 要求为准。
- Windows 安装 CH340 驱动、准备 BurnTool 5.0.39；先确认板子插入后枚举出 COM 口。

### 4.3 官方 OpenHarmony 精简路线参考命令

以下出自已下载的官方指南，**本机尚未完整执行通过**。先按指南安装 `repo` 和依赖，再执行：

源码清单固定为 5.1.0 Release，不照旧教程直接拉不断变化的 master。源码与预编译下载均成功后，按同版本指南安装 hb、配置工具链并构建。

官方示例里 `hb set` 选择的 `nearlink_dk_3863` 是其参考开发板目标，**不是本套件已验证适配的目标**。队友需要确认软通套件的配置，不能仅因芯片相同就烧入参考板固件。

### 4.4 随板 demo 接入方式

套件教程使用的 SDK 路径：

```text
device/soc/hisilicon/ws63v100/sdk
```

把随板 `demo` 复制到 SDK 的 `application/samples/demo`，在 `application/samples/Kconfig` 增加（已有则不重复）：

```kconfig
config ENABLE_DEMO_SAMPLE
    bool
    prompt "Enable the Sample of DEMO."
    default n
    depends on SAMPLE_ENABLE

if ENABLE_DEMO_SAMPLE
osource "application/samples/demo/Kconfig"
endif
```

在 `application/samples/CMakeLists.txt` 中按该版本教程加入：

```cmake
if(DEFINED CONFIG_ENABLE_DEMO_SAMPLE)
    add_subdirectory_if_exist(demo)
endif()
install_sdk("${CMAKE_CURRENT_SOURCE_DIR}/demo" "*")
```

在 SDK 根目录执行套件教程的命令：

```bash
./build.py menuconfig ws63-liteos-app
./build.py -c ws63-liteos-app
```

menuconfig 中只启用本次需要的实验，先选择线程/LED 等基础示例。不要一次打开所有 demo 争用引脚。

教程给出的固件输出：

```text
output/ws63/fwpkg/ws63-liteos-app/ws63-liteos-app_all.fwpkg
```

以上是套件 SDK 路线；是否需要先构建外层 OpenHarmony 组件，取决于取得的完整 SDK/移植包。与官方 `hb build` 路线的入口不同，不能简单混用。

### 4.5 烧录与验收

1. 未接门磁/433MHz 接收模块时，先验证板子 USB COM 枚举。
2. BurnTool 按套件教程选择 WS63，使用本次正确目标生成的 `.fwpkg`，烧录模式/复位时序按原手册执行。
3. 烧录后串口能看到基础示例日志；记录实际串口参数。
4. 分别验证按键、OLED、温湿度，不应出现异常重启或卡死。
5. 第二块板单独重复基础验收，再做两板星闪连接和断线重连。
6. 保存 SDK 版本/提交号、依赖版本、配置文件、编译命令、构建日志和固件 SHA256。能复现编译成功才算环境交付完成。

## 5. 两套板与现有系统的分工（拟定，尚未实现）

| 设备 | 建议职责 |
| --- | --- |
| 原 TX-SMART-R / RK2206 | 保留已有环境监测、屏幕、语音、夜灯、服药提醒和云端链路 |
| 星闪板 A + 智能家居扩展 | 门磁、433MHz 接收模块等房间节点；按空闲引脚和供电核实后接入 |
| 星闪板 B + 手表扩展 | 按键求助、服药确认、心率血氧点测及运动信息；先验证传感器可用性 |

每块底板本阶段只装一种扩展板，两块板共用 SDK、分别保存目标配置和固件。具体哪一块充当星闪中心/网关，待 Wi-Fi 与 SLE 并发验证后确定。

建议先完成：板 A 与板 B 的 SLE 简单数据传输；再逐步增加传感器和业务事件。RK2206 本身不因增加这套板子就拥有星闪通信能力，不能假设可以直接配对；它与新节点的协同可先经 Wi-Fi/后端完成。

433MHz 遥控器仍通过原 433MHz 接收板解码，再把按键事件送给星闪板，并非遥控器直接连接星闪。按键映射等业务后续另行确定。

固定桌面的板载加速度计不能证明老人跌倒；只有实际佩戴且验证的节点才进一步讨论跌倒算法。心率血氧先做接触式点测和有效性判断，不把无效读数当正常健康数据。

## 6. 接线与供电须先核对

- 每套底板先各自 USB 供电，不从 RK2206 的 3.3V 排针给两套底板供电。
- 门磁/433MHz 模块是否可由星闪扩展口供电，需核对原理图、稳压器余量、实际接线和信号电平；**目前未确认，不能承诺不需要额外电源**。
- 之前 RK2206 接外部杜邦线后发生 ADC 变化、传感器异常和重启；拔线恢复。原因没有定论，不能仅凭 ADC 按键电压变化断言电流不够。
- 不沿用 RK 的 B6/B7 等名称给星闪板接线；星闪 GPIO 重新依据本套件原理图分配。
- 不把 5V 输出信号直接送入未确认容限的 GPIO，也不并联两块板的 3.3V 输出。
- 模块信号必须有正确参考地；若未来使用独立电源驱动外设，接地方式要与其信号连接一起设计。

## 7. 与 App / 后端的边界

本次只交接星闪环境，后端/App 未改。

若新增节点独立上云，分配独立设备身份，不能与现有 RK 使用同一 MQTT 设备 ID。若由一个网关汇总，仍需在消息中明确节点来源、类型、时间和有效性。

后续多节点展示、节点离线状态、命令路由可能需要后端/App 配合；本次没有承诺这些已经兼容。云账号密钥和设备密钥不要放进交接包。
