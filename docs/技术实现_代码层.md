## 二、主板：线程 + 锁 + 命令队列

### 2.1 线程划分（`home_safety_example.c`）

| 线程 | 行 | 干什么 | 为什么单独开 |
| --- | --- | --- | --- |
| `wdt_thread` | 105 | 喂狗 + 检查心跳陈旧 | 心跳停了就不喂狗，让系统自己复位 |
| `nfc_init_thread` | 129 | 每 5 秒写 NFC 标签 | 标签 I2C 写可能失败重试，不能占启动流程 |
| `body_read_thread` | 150 | 只读 PIR | **人体响应不能被 I2C 重试拖慢**（代码注释原话） |
| `sensor_read_thread` | 163 | SHT30 / MQ2 / 光照 / 门磁 | 慢速 I2C 设备，独立节奏 |
| `safety_monitor_thread` | 252 | **核心状态机**：判定、报警、上报、执行命令 | 单一消费点，避免多处并发改状态 |
| 网络 / MQTT / 按键 / 语音 | 759-838 | 各自 `LOS_TaskCreate` | 阻塞式 socket 不能和主循环共用 |

**关键点**：`LOS_TaskCreate` 在 759–838 行集中创建，**锁在任何业务线程之前创建**（`safety_runtime.h:20` 注释：Locks are created before any application task starts）——否则会出现"任务先跑、锁还没建"的竞态。

### 2.2 三把锁，分层不嵌套（`include/safety_runtime.h:22-35`）

```c
int  safety_i2c_lock(void);      // 总线锁：所有 I2C 事务
void safety_lock(void);          // 状态锁：报警位、灯、服药状态
void safety_storage_lock(void);  // 存储锁：KV 落盘
```

- **I2C 锁有 try 版本**（`safety_i2c_try_lock`）+ 超时计数，超时就放弃本次采样而不是死等 → 一个坏传感器不会拖死整机。
- 三个锁**不交叉持有**：先拿总线锁做完事务就释放，再拿状态锁更新结果，杜绝死锁。

### 2.3 命令队列：HTTP/MQTT/语音统一入口

```c
int safety_command_submit(int code, const char *source, unsigned int *id);
int safety_command_take(safety_command_t *cmd);
void safety_command_done(const safety_command_t *cmd, int result);
```

- 三种来源（云端 MQTT、本地网页 HTTP、板上语音）**都只往队列里塞**，由 `safety_monitor_thread` 单点执行 → **所有状态变更只有一个写入者**。
- 每个命令有 `id` + `code` + `result`，执行完写回执；HTTP 立刻返回"已受理"，页面再轮询结果。
- 命令码定义在 `safety_runtime.h:7-18`：`ACK / MUTE / LIVING / MEDICINE / MEDICINE_PLAN / MEDICINE_STATE / LIGHT / SOS / UNMUTE / CONTACT / CARE_POLICY / CARE_PAUSE`。

### 2.4 配置：整包校验 + KV 落盘 + revision

```c
typedef struct {
    char wifi_ssid[33], wifi_pass[65], broker[96], client_id[96];
    unsigned int port, report_ms, noact_ms, mute_ms;
    double temp_low, temp_high, humi_low, humi_high, gas_limit;
    bool demo;
} safety_config_t;
```

- `safety_config_set()`：**全部字段一起校验，全部通过才写 KV**（注释：All changes validated together before any KV write）→ 不会出现"温度改成功、湿度改坏"的半套配置。
- 校验范围写死在 `safety_runtime.c:87-93`：`report_ms ∈ [1000, 3600000]`、`noact_ms ∈ [10000, 86400000]`、`mute_ms ∈ [1000, 600000]`、`temp_low < temp_high`、`humi ∈ [0,100]`。
- 网络类改动（SSID/密码）**明确要求重启生效**，不在运行时热切 —— 避免半连接状态。

### 2.5 报警判定与边沿

```c
// home_safety_example.c:507
env_alarm = v->temp < cfg.temp_low || v->temp > cfg.temp_high || ...
// :510
bool gas = v->gas_ppm > cfg.gas_limit, smoke = v->gas_ppm > SMOKE_PPM_LIMIT;
```

```c
// safety_logic.c:57
void safety_alarm_edges(const bool alarms[5], bool previous[5], unsigned int *rising, ...);
```

- 只有 0→1 / 1→0 才产生事件 → **同一次燃气泄漏只播报一次**，不会每轮循环叫一遍。
- 事件进 16 条环形事件表（`SAFETY_EVENT_COUNT`），上报时带 `event_revision`，App 靠它判断"有没有新事件"。

## 三、本地 HTTP 服务：一张路由表 + 双通道鉴权

`src/net_server.c`（`:386` 路由表、`:399` 起分发）

| 路径 | 方法 | 鉴权 | 作用 |
| --- | --- | --- | --- |
| `/status` | GET | **不需要配对** | 只读状态，供网页首屏 |
| `/pair/status` `/pair/request` `/pair/cancel` | GET/POST | 不需要 | 配对流程 |
| `/config` `/ack` `/mute` `/living` `/medicine` `/light` `/care-pause` `/care-policy` `/messages/*` | POST | **必须 `client_identity`** | 一切写操作 |

```c
// net_server.c:419
if(strcmp(url,"/status") && !client_identity){
    http_reply(fd,401,"{\"error\":\"physical_pairing_required\"}"); return;
}
```

- **读和写分开授权**：不配对能看状态（老人自己打开就能看），要操作必须先在板上确认。
- Bearer 是从 `X-Care-Local` / Cookie 里取 64 位十六进制 token，`local_access.c:21` 逐字符校验 `isxdigit`，长度必须 64。
- 配对：`REQUEST_TTL 60 秒`（请求 60 秒内有效，过时自动作废）、`PAIR_TTL 30 分钟`（授权有效期）、**最多 4 个会话**（`sessions[4]`，超了要踢一个）。

### NFC 那一层（`src/nfc_tag.c`）

```c
// nfc_tag.c:37
int nfc_tag_set_ipv4(const char *ip)
```
- `:53` 先比 `written_ip`，相同直接返回 → **不重复写标签**（延长标签寿命、减少 I2C 失败面）。
- `:42` 校验 `strlen(ip) < 16`，失败返回 0 且**不缓存成功**，下一轮重试。
- 写入的是一条单记录 URI：`http://<ip>:8080/`，不含任何凭据。

## 五、App：services 分层 + 1 秒 tick

### 5.1 分层

```
pages/       UI（Index / Camera / Messages / CareSettings / Nodes / DeviceContact / LocalControl）
services/    Backend（HTTP+WS 封装）、CameraFeed、CameraConnection、DeviceSession、Voice*
models/      纯数据结构与纯函数（AlarmState、Messaging、CarePolicy、Permissions）
theme/       颜色与字号（CareTheme）
```

**规则**：`pages` 不直接调 `http.createHttp()`，一律走 `services/Backend.ets` 的 `request()`。

### 5.2 HTTP 封装（`services/Backend.ets:81`）

```ts
async request(path, method, body='', readTimeout=45000): Promise<Envelope>
```
- 统一注入 `Authorization: Bearer`、`Cache-Control: no-store`、`_ts=Date.now()`（**破 WebView/代理缓存**）。
- `connectTimeout 20000 / readTimeout 45000`，摄像头这类大响应单独传更长的 `readTimeout`。
- 401 时清 token 并抛"登录已过期"——**单一出口处理登录态**，页面不用各自判断。
- 自签证书：`options.caPath = certificatePath()`，证书放应用沙箱，不在代码里硬编码。

### 5.3 WS：先换票据再建连（`Backend.ets:160-181`）

```ts
const reply = await this.request(`/api/v1/ws-ticket?device_id=...`, POST, '{}');
const socket = webSocket.createWebSocket();
socket.on('message', (_e, raw) => { ... });
```
- **不用 access_token 直接连 WS**：先换 30 秒票据，票据泄露的窗口只有 30 秒。
- 收到消息 → 更新 `@State` → ArkUI 自动重渲染；WS 断了靠 1 秒 tick 里比对 `deviceTime` 再补拉。

### 5.4 通知只带路由键（`services/AlarmNotifications.ets`）

```ts
// Notification taps retain only a routing key, never credentials or health records.
wants:[{ bundleName:'com.zhian.eldercare', parameters:{ alarm_device:device, alarm_key:key } }]
```
- 通知 ID 用 `device+key` 的字符串哈希算（保证同一条报警不重复堆叠）。
- 点击通知只恢复"看哪条报警"，**不带 token、不带健康数据**。

### 5.5 摄像头取帧循环（`services/CameraFeed.ets:16-45`）

```ts
startPolling(base, user, password, onFrame, onEnd, intervalMs = 1000)
```
四个细节，每个都是踩坑换来的：

1. `' Basic '` **前面的空格不能省** —— OpenHarmony 拼 header 时不加空格，而 ESP32 侧固定跳过一个字符（代码里有注释）。
2. 每帧 `http.createHttp()` → `request` → **`finally { client.destroy() }`** —— 不 destroy 会漏连接。
3. `misses >= 5` 才 `onEnd()`，失败后 500ms 快速重试，**不是立刻放弃**。
4. `generation` 计数器：页面切走时 `generation++`，旧循环在 await 回来后自己退出，**避免两个循环同时打摄像头**。

### 5.6 每帧 1 秒的真正原因（注释原文）

```ts
// 连续 40 秒后 PCB 池耗尽，accept 拿不到资源，整机从网络消失且不自行恢复（需断电）。
// 1 秒/帧（省流）在同样硬件上连测 30 次全通、可长时间稳定。故局域网固定 1 秒/帧。
```

## 八、最值得主动讲的 6 个技术点

1. **单点写入**：所有状态变更走命令队列，`safety_monitor_thread` 是唯一消费者 → 没有并发写状态的问题。
2. **锁分层不嵌套**：I2C 锁 / 状态锁 / 存储锁，先做完硬件事务再更新状态，杜绝死锁和优先级反转。
3. **配置整包校验**：全字段通过才落盘，配合 `revision` 防回滚。
4. **边沿触发 + 事件表**：报警只在状态翻转时产生事件，避免重复播报/重复推送。
5. **短票据代替长 token**：WS 和取图都先换 30 秒票据，凭据不进 URL、不进日志。
6. **确定性退避**：摄像头 2→4→8 秒退避、取帧失败 500ms 快重试、MQTT 10 秒重连——**每个网络组件都有明确的退避策略**，而不是无限快速重试把设备打死。

## 九、能耗/实时性的取舍（被问就答这个）

- 采样：PIR 单独线程高频、I2C 传感器低频，**贵的操作不放在快路径上**。
- 上报：`report_ms` 可配，演示 1 秒、日常拉长到分钟级。
- 摄像头：空闲不上传，有人看才传，1 秒/帧。
- NFC：地址不变就不重写标签。
- 结论：**"实时"只给真正需要实时的地方（人体、报警），其余全部走批量/退避。**
