本包完成账号管理与设备联系消息代码接入，软件测试通过，尚未部署服务器、烧录 v3.5.57 或安装到手机实测。当前生产服务不会因生成本包而改变。

## 队友部署顺序

1. 备份服务器现有源码、SQLite 数据库和 .env，核对是否有新的未合入代码。
2. 线上是 1.10 时审阅 backend_1.10_to_1.12.diff；已应用本次 1.11 账号增量时审阅 backend_1.11_to_1.12.diff。选择对应的一份，不要同时应用。是普通 unified diff，可在后端根目录用 patch -p1 --dry-run < 对应文件 检查，再应用；不是 git am 邮件补丁。
3. 保留生产 .env、数据库和证书，按原虚拟环境运行 python -m unittest discover -s tests -v。新增表自动创建，不删除原有数据。
4. 按既有方式重启 API，检查 /healthz 的 api_version=1.12.0。AMQP 消费进程沿用原有启动方式，确认设备消息转发规则覆盖 device.message 上报。
5. 在主板产品 HomeSafety 服务下增加 contact 命令。原有命令和属性保留。参数见下表。云端只有接受命令，并不能证明主板执行，需继续查看执行回执。
6. 烧录 Firmware.img，版本确认 v3.5.57；安装 App 1.15.0。后续按总交接清单集中联调。

| contact 参数 | 类型/值 |
|---|---|
| action | 字符串 reply 或 seen |
| boot_id | 整数，原消息的启动编号 |
| message_id | 整数，原消息编号 |
| code | 整数 0..3；seen 用 0；reply 用 1..3 |
| request_id | 字符串，reply 为后端生成的 64 位摘要；seen 为空字符串 |

contact 为新增命令，不需要新增 contact_event 物模型属性：contact_event 走现有 messages/up 消息上报与 AMQP 转发。必须部署新的消费入口/API 才能识别新消息名称，旧后端会拒收。

## 账号管理

包含 1.11 的一次性邀请、独立注册、登录设备管理、密码修改、移出家庭与本人注销。具体接口见账号交接说明。1.12 允许已移出家庭的独立账号查询空家庭清单，供 App 接受新邀请；该账号仍不能读取原家庭设备。

家庭管理员和服务器初始化账号受注销保护。目前不提供管理员转让、自助找回密码或注销整个家庭；这些不应显示为已完成。

## 设备消息接口

GET /api/v1/devices/{device}/messages?after=0&limit=100
返回 items、next_cursor、has_more、merge_key。按 cursor 升序分页补拉；客户端用 boot_id+message_id 合并，revision 高的覆盖低的。不能按单一 message_id 合并不同次启动。

POST /api/v1/devices/{device}/messages/{boot}/{message}/reply
请求 {code:1..3,client_request_id:"客户端稳定编号"}。

POST /api/v1/devices/{device}/messages/{boot}/{message}/seen
请求 {client_request_id:"客户端稳定编号"}。

返回 202 代表已提交。根据 command_id 查询现有 /api/v1/commands/{command_id}。executed 只表示主板已执行；老人看到家人回复，需要主板 K6 确认，之后 contact_event 中 family 消息的 seen=true。超时/unknown 不能显示为送达或已读。

读消息要求家庭 view 权限；回复和向主板标记已读要求 control。只支持当前家庭守护主机，手表/环境节点不会混入此通路。账号聊天依然走 conversations/messages 接口。

服务器持久化设备消息、去重和已读变化，App 离线后按游标补拉。主板只保留最近 16 条本地消息与待上报变化，MQTT QoS1 成功回执后才标记已发布；断线会重试。主板断电会丢失尚未上传的内存消息，不能宣称主板具备断电持久离线信箱。
