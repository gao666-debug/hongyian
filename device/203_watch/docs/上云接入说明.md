# 手表上云接入说明（IoTDA → 后端）

把 WS63 手表接到华为云 IoTDA，并让 `backend/` 收到、存下、推给 App 的完整链路。
参数在 `src/hy_cloud_cfg.h`（由 `hy_cloud_cfg.example.h` 复制），本文件只说**为什么**和**怎么验证**。

## 1. 云侧要准备什么

| 项目 | 位置 | 说明 |
| --- | --- | --- |
| 接入域名 | IoTDA 控制台 → 总览 → 接入信息 | 设备侧是 `iotda-device`，不是 `iotda-app`；后者只给服务器用 |
| 设备 ID / 密钥 | 设备 → 设备详情 | 密钥是注册设备时给的那串原文 |
| 服务 ID | 产品 → 模型定义 | **必须逐字一致**，本项目实测是数字 `11` |
| 8 个属性 | 同上 | `heart_rate` `spo2` `accel_x` `accel_y` `accel_z` `steps` `fall_state` `fall_count`，均为 int |

固件上报的报文：

```json
{"services":[{"service_id":"11","properties":{
  "heart_rate":60,"spo2":100,
  "accel_x":-188,"accel_y":-168,"accel_z":951,
  "steps":2,"fall_state":0,"fall_count":0}}]}
```

主题：`$oc/devices/{device_id}/sys/properties/report`。

## 2. 上电后的完整链路

```
uapi_wifi_init → STA 关联 → DHCP → SNTP 取 UTC 时间 → MQTT CONNECT（HMAC-SHA256 签名）→ 每 10 s 上报
```

缺任何一步都连不上，串口里会明确打出来（`[hy-net]` / `[hy-cloud]` 前缀）：

```
[hy-net] 拿到 IP: 192.168.x.x gw=192.168.x.1
[hy-cloud] clientId=<dev>_0_1_2026110103
[hy-cloud] 已连上华为云 IoTDA
[hy-cloud] 上报 hr=60 spo2=100 steps=2 fall=0(0次) 线上=1
```

## 3. 三个必须知道的坑

### 3.1 服务 ID 对不上 = 静默丢弃

平台的属性上报是**单向**的：服务 ID 找不到、属性名/类型对不上，平台直接把报文扔掉——
**不断开连接、不返回错误**。于是会出现"控制台显示在线、串口一直打印上报成功、物模型数据却一直是空的"。

定位手段（不用烧板子、不用反复试）：用 `tools/hw_iotda_shadow.py` 查设备影子。

- 影子 `reported` 不更新 → 报文被拒（服务 ID / 属性名 / 类型）
- 影子更新了 → 平台收到了，问题在展示或后端侧

更快的办法：一条连接里连发多个候选 `service_id`（各配不同数值），再查影子，
哪个值进去了哪个就是真 ID——本项目就是这样一击命中 `11` 的。

### 3.2 明文 1883 强制校验时间戳

`HY_HW_SIG_TYPE=1` 时平台校验 ClientId 里的 `YYYYMMDDHH`（UTC），偏差过大直接拒连。
所以板子必须先 SNTP 拿到时间再连 MQTT，顺序不能换。
用 8883 加密可以换另一种签名类型，但要多占约 3 KB 内存、多几百毫秒握手。

签名公式容易写反，注意 **key 是时间戳、消息才是设备密钥**：

```
password = HMAC-SHA256(key=时间戳, msg=设备密钥)
```

控制台下载的 `DEVICES-CONNECT-KEY-*.txt` 里 `password` 是**算出来的结果**（每小时变一次），
不是设备密钥本身，不能直接写进固件。反证方法：把密钥改成 32 个 0，
CONNACK 立刻返回 `0x04`；换回真密钥返回 `0x00`。

### 3.3 `tcpip_init` 没跑 = 所有网络 API 拿不到资源

SDK 启动流程里 `tcpip_init()` **只有一个调用点**：`wifi_host_task` 内，
且只有 `uapi_wifi_init()` 返回 0 才往下执行。这条链一断，`lwip_init → memp_init` 全没跑，
内存池全是空的。表现非常迷惑：

- WiFi 能扫描、能关联、四次握手全过（走驱动层，不经过 lwip）
- 但 `socket()` 返回 `-1 / errno=105(ENOBUFS)`，`dhcp_start` 返回 `-1(ERR_MEM)`
- 而 `mem_malloc` 正常（走 libc，不依赖 memp）

`hy_net.c` 里的做法：先做 7 项分配探测（`mem_malloc` / `pbuf_ram` / `pbuf_pool` /
`udp_new` / `tcp_new` / `netconn` / `socket`），成功项少于 3 就补一次
`tcpip_init(NULL, NULL)`（幂等，重复调用是空操作），再测一遍。

顺带排除过的三个错方向，别再走：网卡 MTU=0、DHCP 起太早、信号量上限 32。

## 4. PC 端先验证，再烧板子

```bash
# 三元组连通性：算签名 → CONNECT → 发一条属性 → 打印 CONNACK
python tools/hw_iotda_probe.py <域名> <设备ID> <设备密钥> [服务ID]

# 设备影子：平台到底收没收到、服务 ID 到底叫什么
python tools/hw_iotda_shadow.py <域名> <设备ID> <设备密钥>
```

`hw_iotda_shadow.py` 会用同一个 clientId 连接，板子会被挤下线几十秒后自己重连——属正常现象。

## 5. 后端侧

后端不直连 MQTT，走 AMQP 订阅 IoTDA 的属性上报通知：

```
IoTDA 属性上报 → AMQP 队列 → consume_cloud.py → POST /api/v1/iotda/notifications
              → backend/watch.py（校验+归一化）→ SQLite + WebSocket
```

配置（`.env`）：

```bash
WATCH_DEVICE_ID=<手表在 IoTDA 上的设备 ID>
WATCH_SERVICE_ID=11
IOTDA_SERVICE_ID=HomeSafety     # 主板服务 ID，保持原值
```

接口与字段约定见 `backend/README.md` 的「手表数据接入」一节。
