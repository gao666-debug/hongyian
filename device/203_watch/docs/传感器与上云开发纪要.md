## 1. 目标与物件

| 物件 | 说明 |
| --- | --- |
| MCU 底板（EXB） | 海思 WS63，RISC-V + LiteOS，XIP 从 QSPI0 取指 |
| 手表扩展板（WEAR） | 黑色小板，插在底板双排 12 针上；带 **7 针圆屏座**、10 针 `J2`、LDO `U3` |
| 圆屏 | 1.28 寸 GC9A01，240×240，**7 针**：1 VCC(5V)、2 GND、3 SCL、4 SDA/MOSI、5 DC、6 CS、7 RST |
| 传感器 | MPU6050（0x68）、MAX3010x（0x57）——**实测在底板上，不在 WEAR 上** |

### 引脚分配（已固定，不再扫）

```
SCL=IO7   MOSI=IO9   DC=IO10   CS=IO11   RST=IO12     VCC=5V0   GND
```

### 三个必须记住的坑

1. **`IO6 / IO13 / IO14` 被扩展板接地**——当 SDA 永远读 0，会制造假命中。
2. **`ADO` 在 `J2-7`**，是 MPU6050 的地址脚；`RST` 只在 `J1-6`，`PIJ204` 是 `NLSensor0INT`，不是 LCD 复位。
3. **`IO0~IO5` 会硬 fault**；开机打印的 `Flash Init Fail 0x80001341` 是**常态**，不是坏块。

## 2. 排查走过的路（按结论分，不按时间）

### 2.1 一次性排除掉的（有实测数据）

| 假设 | 怎么排的 | 结果 |
| --- | --- | --- |
| 引脚映射错 | 6 个可用脚、360 组 `(clk,mosi,dc,cs)` 全排列扫描 | **0 命中** |
| 引脚之间短路 | 三态 `up/dn/drv` 建短路图 | 5 根互不相连，**无桥接** |
| 软件 SPI 太快 | 实测整帧 9.6 s ÷ 115,200 字节 | 仅 **≈96 kbit/s**，远低于 GC9A01 上限 |
| CS 边界拆错 / 地址窗口越界 | 队友独立实现：一命令连同参数一次 CS，整帧一次 CS，0..239 闭区间 | 仍灰 → **排除** |
| 初始化序列缺项 | 50 条厂商序列，含 `0x11`+120ms、`0x29`+20ms、`0x3A=0x05`、`0x36=0x08` | 仍灰 → **排除** |
| 是我们自己写的代码有问题 | 单独跑官方原始 `200_lcd_display` 例程 | **也灰** → 排除 |

### 2.2 控制器有没有在总线上应答

对 GC9A01 做**写-读回比对**（如果控制器活着，读回值应该等于写入值）：

```
COLMOD(0x3A) 写 0x66 → 读 FF
MADCTL(0x36) 写 0x48 → 读 FF
RDDID(0x04)           → FF FF FF FF
```

**写进去读不回** ⇒ 控制器没有应答。保留意见：7 针模组没有 MISO，读回本身依赖 SDA 双向，
所以这条不能 100% 证明控制器死了，只能说明"总线上没有活的从机"。

### 2.3 I2C 那条线：一次被截断的错误码

老代码用 `char ret` 接 `errcode_t`（uint32_t）返回值，**32 位被截成低 8 位**：

| 完整码 | 含义 | 截断后看到的 |
| --- | --- | --- |
| `0x80001313` | **I2C_TIMEOUT**（总线超时） | `19` |
| `0x80001314` | I2C_ACK_ERR（从机没应答） | `20` |

改成完整打印后真相是 **TIMEOUT 而不是 ACK_ERR**——方向完全不同：超时查总线电平，ACK 错才查器件。

### 2.4 三组对照，把责任域一刀切开

| | 底板 + 原 WEAR | 只留底板（WEAR 拔下） |
| --- | --- | --- |
| SCL 空闲 | 1（正常） | 1（正常） |
| **SDA 空闲** | **0 / 0（被拉死）** | **1 / 1（正常）** |
| MAX3010x `0x57` | `0x80001313` TIMEOUT | OK，`PART_ID=0x11` |
| MPU6050 `0x68` | `0x80001313` TIMEOUT | OK，`WHO_AM_I=0x68` |

结论：**原 WEAR 板把 I2C SDA（`IO15` / `J1-2`）稳态拉到地**，而且事务前后都是 0，是静态拉死而非传输卡住。
同时证明**两个传感器在底板上、从未损坏**。

### 2.5 队友版本里发现的真 bug

`lcd_bringup.c` 的 `output()` 先在引脚还是**输入**状态时写电平，再设方向：

```c
uapi_pin_set_mode(pin, 0);
level(pin, idle);                                              // ← 此时是输入脚
if (s_error == 0) uapi_gpio_set_dir(pin, GPIO_DIRECTION_OUTPUT);
```

WS63 的 HAL 会直接拒绝：`0x80001006 = ERRCODE_GPIO_STATE_MISMATCH`。
第一个被配置的是 `CS=IO11`，于是程序在第一条命令之前就退出，**一个字节都没发**。
主机测试没发现，因为 `tests/test_lcd.c` 里的 `uapi_gpio_set_val()` 桩**永远返回 0**。

修复补丁：`D:\ws63\fix-gpio-order.patch`（把 `set_dir` 提到 `set_val` 之前）。

### 2.6 镜像污染：两个显示入口挤在同一份固件里

上一版固件的启动日志里，同一次启动出现三个标记：

```
[hy-lcd] BUILD=HY-LCD-ONLY-1 Oct 31 2026 14:52:47
demo 200_lcd_display hello world!
[hy-lcd] init bytes sent; this does NOT confirm visible display
```

`200_lcd_display` 的引脚是 **7/9/12/10/11，和最小测试固件完全相同**，而且通过 `app_run()` 注册——
只要目标文件被链进去，开机就会自己跑，两个任务抢同一组线。

**但根因不是配置，是静态库的陈旧成员**：`libsamples.a` 里一直留着早先做 200 基线时的
`main.c.obj`，`build.ninja` 早就没有它了，链接时却照旧带进镜像。

| | 清理前 | 清理后 |
| --- | --- | --- |
| `libsamples.a` | 525,250 字节 | 46,920 字节 |
| `ws63-liteos-app.bin` | 1,313,152 | 1,292,160（小 21 KB） |

清理后单入口、帧循环 `rc=0`、**屏仍然灰** ⇒ 双入口争用被排除。

## 3. 被推翻的判断（这一段最重要）

排查里最贵的不是没结论，是**拿错误结论继续往下推**。以下是明确推翻的：

| 曾经的判断 | 为什么错 |
| --- | --- |
| "RC 线材电容法能判断断线" | 内部下拉只有几十 kΩ，pF 级根本测不出；`t=0` 不能当断线证据 |
| "400 kHz 时钟" | 那是按 `NOP` 估算的；实测整屏 18 s 折算只有 **51 kHz**，后来版本 96 kbit/s |
| "供电已排除，因为背光亮" | **站不住**：背光走 5 V 不经 LDO，`U3` 输出从未实测 |
| "v26 扫到屏了" | 假命中：`IO13` 被外部拉低永远读 0，被当成屏回 `00 00 00` |
| "Flash Init Fail 是坏块" | 每次开机都打印，是**常态**；为此多按了两次 RST，白折腾 |
| "屏 + MPU + MAX 三路同时失效，共因是 3V3 或排针" | **错**。拔掉 WEAR 后两个传感器都正常，是 WEAR 把总线拖死 |
| "SDA 恒低 = 从机没供电被 ESD 钳位" | **不成立**。从机有电且能应答，是 WEAR 侧的真短路/误连 |
| "只屏 + 底板也灰，所以屏坏了" | **实验无效**。屏一直在 WEAR 座上，WEAR 实际没拔；且 SCL 可能经 WEAR 的 `J2-8` 转发 |
| "双入口抢 IO 是灰屏原因" | **已排除**。清成干净单入口后仍然灰 |

一条通用教训：**类型截断会骗人，增量构建会留死代码，主机测试桩不模拟状态机就测不出真问题。**

### 三条待测（都在硬件侧，不需要示波器）

**通电**，直流档，表笔探屏模组一侧：

| 测点 | 正常应有 | 读数异常的含义 |
| --- | --- | --- |
| 模组 `VCC`(1) 对 GND | 5 V | 没有 → 座子 1 针断 |
| **`U3` 输出** | **3.3 V** | 没有 → **控制器没电**（最符合当前现象） |
| `CLK`(3) 对 GND | 约 1.5~2 V 中间值（在翻转） | 0 或 3.3 V 不动 → 时钟没到屏 |
| `CS`(6) 对 GND | 整帧期间接近 0 V | 恒 3.3 V → CS 没接到 |
| `RST`(7) 对 GND | 初始化后保持 3.3 V | 恒 0 V → RST 断/被拉低 |
| `DC`(5) 对 GND | 大部分时间约 3.3 V | 恒 0 V → DC 断 |

> **量 `U3` 之前必须先看清丝印型号**——SOT-23 与 SOT-89 的三脚定义不同，不能凭封装猜。
> `CLK` 读到中间电压这一条最有价值：它是"信号真的到达屏"的直接证据，主控自身回读替代不了。

### 通断（**务必断电**，蜂鸣档）

一支表笔固定在 `LCD1` 的脚上，另一支把整排 12 针逐针点一遍——不数针、不管丝印方向，响的那根就是它。

| 从 `LCD1` 焊盘 | 找 | 含义 |
| --- | --- | --- |
| 3（SCL） | 左排 12 针 | 不响 = 时钟经 WEAR 转发，必须插回 WEAR 才有意义 |
| 4（MOSI） | 右排 12 针 | 不响 = 数据线断 |
| 5 / 6 / 7（DC/CS/RST） | 同一排 | 有不响 = 底板到座子之间有断点 |

### 交叉替换顺序

**整块 WEAR → 只换屏 → 只换传感器**，每次只动一个变量。

## 8. 传感器点亮（2026-11-01 08:05，固件 `HY-SENSOR-1`）

屏的问题先放一边，加速度和心率血氧已经跑通。

### 8.1 实测证据（串口原文）

裸板（拔掉 WEAR）：

```
[hy-sensor] A 段 空闲电平 SCL=IO16:1 SDA=IO15:1
[hy-sensor]   MPU6050 0x68 写=0x80001314 (ACK_ERR 从机无应答)
[hy-sensor]   MAX3010x 0x57 写=0x80001314 (ACK_ERR 从机无应答)
```

插上 WEAR：

```
[hy-sensor]   MPU6050 0x68 WHO_AM_I=0x68
[hy-sensor]   MAX3010x 0x57 PART_ID=0x11
[hy-sensor] MPU6050 PWR_MGMT_1=0x00 (已唤醒)
[hy-sensor] MAX30100 MODE=0x03 (SpO2 模式已启动)
[hy-sensor] ===== VERDICT bus=1 SCL=IO16 SDA=IO15 MPU=OK MAX=OK =====
[hy-sensor] acc ax=  -80 ay= -150 az=  965 mg | steps=1 | hr=0 spo2=0
[hy-sensor] max3010x raw: ir_max=11808 ir_min=4960 swing=6848 red_max=7168   ← 手指放上去
```

### 8.2 两条被推翻的旧结论

| 旧结论 | 本轮实测 |
| --- | --- |
| 「传感器在底板上，不在 WEAR 上」 | **错**。裸板两个地址全是 `ACK_ERR`，插上 WEAR 才应答 → 与 WEAR V0 原理图一致（U1 MAX30100 / U2 MPU6050） |
| 「原 WEAR 把 I2C SDA 拉到地」 | **当前这块 WEAR 没有**：上电即 SCL=1 / SDA=1，总线健康。之前那次可能是屏座/排针没插正 |

**教训**：`ACK_ERR` 和 `TIMEOUT` 必须分开看——`ACK_ERR` = 线好、器件不在；`TIMEOUT` = 线本身有问题。
这次两个地址都 `ACK_ERR`，直接把「裸板有传感器」这条排掉了。

### 8.3 引脚与配置（已验证）

```
I2C1: SCL=IO16(mode2)  SDA=IO15(mode2)  bus=1  100kHz   ← 与官方 201/202 一致
MPU6050   0x68   ±2g(ACCEL_CONFIG=0x00, 16384 LSB/g)  采样 200Hz 配置，读取 50Hz
MAX30100  0x11   MODE=0x03(SpO2)  SPO2_CFG=0x2C  LED_CFG=0x77  FIFO 每对 4 字节
```

旧 `watch_sensor.c` 里 SCL/SDA 是写反的（`SCL=15, SDA=16`），本轮已按官方例程改正，
并保留三组引脚自动尝试（`(16,15)` / `(15,16)` / `(18,17)`）。

### 8.4 心率那个「翻倍」陷阱

第一次算出 **146 bpm**，而实际静息心率约 73——正好 2 倍。
原因是芯片实际出点约 200 Hz，算法按 `FS=100` 在算。MAX30100 与 MAX30102 的
`SPO2_CONFIG` 位定义不同，厂商例程把 `0x47`（30102 的值）套在 30100 上，很容易踩。

处理办法：**不猜寄存器，数出来**。每 2 秒统计真实点数算出抽点倍数，保证喂给算法的永远是 ~100 Hz。
日志里 `| 200Hz/2` 就是「实测 200Hz、每 2 点取 1 点」。

| 采样率 ≈ 199 Hz | 日志每行尾部 `198~199Hz`，与 buf 计数器吻合 |
| 手指放上去 IR 有明显响应 | `ir_max` 从 2000~3600 → 11000~26000 跳变 |
| 血氧数值稳定合理 | 96~100%，`valid=1` |
| 心率数值不可用 | 算法给 260~666 bpm，兜底过零法给 0（间隔全被 400ms 下界拒掉） |

**已经排掉的**：

- 不是采样率假设错——`FS` 从 100 改到 200、并取消抽点，数值没有改善；
- 不是没手指——`ir_max=14336`、`幅度 3~4%`，有反射但不干净；
- 不是 SCL/SDA 接反——两种组合都能 ACK，且都读到正确 ID。

**下一步只剩两条，都要一次烧录**：

1. **关掉 LCD 再测**（`hy_sensor_main.c` 里 `HY_LCD_ENABLE` 改 0）。
   怀疑背光 5V 与 LDO 3.3V 共地噪声串到 MAX30100 的 VIN。
2. **打波形快照**（每 10 点取 1 点、一次打 100 点）。
   如果波形里出现成对重复值（`A A B B`）或固定 15~16 点周期，
   那就是 FIFO 读指针重叠，问题在读取逻辑而不是生理信号。

> 判断依据：兜底过零法给出 0，说明交流分量里有大量 400ms 以内的“峰”，
> 高频成分压过了脉搏。真正的脉搏波不会这样。

### 8.7 心率为什么是 0（HY-SENSOR-5 诊断，2026-11-01 08:45）

一次性回答了三个问题，全部有原文证据。

**1）0 是门限的结果，不是没数据**

`心率=0 bpm(算法=260/1,兜底=0)` 里，Maxim 给 260/333/600/666（它自称 valid），
被 `35<hr<180` 全部拒掉；兜底过零法要求 ≥3 个合格间隔，也没凑够。

**2）根本原因：芯片只出 11 位有效数据，且基线漂移比脉搏大**

原始字节直接打出来了：

```
#00  27 E0 43 A0   A red=10208 ir=17312
#01  27 A0 44 60   A red=10144 ir=17504
```

低位字节只出现 `00/20/40/60/80/A0/C0/E0` —— **低 5 位恒为 0，有效 11 位、左对齐**。
64 组样本里「低 5 位非零」的个数是 **0/64**。所以这不是拼字拼错，是芯片输出本身如此。

四种拆法对比（相邻差中位数越小越连续）：

| 拆法 | swing | 低5位非零 | 相邻差中位数 | 结论 |
| --- | --- | --- | --- | --- |
| A `(b2<<8)\|b3` 当前 | 320 | 0/64 | 64 | **正确** |
| B `(b3<<8)\|b2` | 57343 | 64/64 | 24575 | 错（字节序反） |
| C `(b0<<8)\|b1` | 256 | 0/64 | 32 | 这是 RED 通道，合理 |
| D `(b1<<8)\|b0` | 57343 | 64/64 | 16384 | 错 |

同时那 5 秒窗口 `swing=5536 / ir_max=22272 = 24%` —— 里面大半是手指移动造成的**基线漂移**，
不是脉搏。过零法门限按「整窗 swing/3」取，被漂移抬高，真实脉搏过不去 → 兜底恒 0。

**3）新踩到的坑：长打印会把 FIFO 打停**

上一版一次打 200 点波形（约 1.5 KB），串口阻塞期间 MAX30100 的 16 深度 FIFO 溢出，
之后**采样彻底停摆**：`buf=601/1000` 卡死、速率掉到 `0Hz`、再无 recalc，只有加速度还在动。
这说明 MAX30100 溢出后不会自己恢复。已在任务循环里加自愈：连续 500 ms 无样本就复位
读写指针并清溢出计数。**结论：以后任何波形/原始值打印都必须短，或分块。**

### 8.8 HY-SENSOR-6 的改动

| 项 | 旧 | 新 |
| --- | --- | --- |
| 增益 | SPO2_CFG=0x2C（4096 nA） | **0x0C（2048 nA，DC 从 27%→约 54%，交流同步翻倍）**，并回读 0x07/0x09 确认写入；ir_max≥62000 自动退回 0x2C |
| 心率算法 | Maxim 为主 + 过零兜底 | **去漂移（1s 滑动均值）+ 5 点平滑 + 局部极大值 + 间隔中位数**，Maxim 只作参考打印 |
| 抗单窗误判 | 无 | 连续 5 窗取中位数投票 |
| 打印 | 一次 200 点波形 | 40 点波形 + 8 组原始字节 |
| FIFO 卡死 | 只能重启 | 500 ms 自愈复位 |

### 8.9 心率跑通（HY-SENSOR-9，2026-11-01 09:15）

**结论：心率可用。** 静息实测 53~60 bpm，42 个窗口里 39 个有值（93%）。

```
[hy-sensor] 心率=59 bpm | 自相关=63(相关度0.630) 峰值=55(间隔3个) 本窗=59 | 幅度=717 漂移=253 | Maxim=333/1 血氧=97%(1)
[hy-sensor] 心率=54 bpm | 自相关=55(相关度0.713) 峰值=52(间隔3个) 本窗=53 | 幅度=756 漂移=250 | Maxim=315/1 血氧=97%(1)
```

自相关与峰值法两条独立路径给出 52~68，互相印证；Maxim 仍给 315/428，**已确认不可用，只留作参考打印**。

#### 三个真正的坑（都在自己代码里，不在硬件）

| 坑 | 现象 | 原因 |
| --- | --- | --- |
| 相关度恒 0.000 | 20 个窗口全是 0 | `long` 在这颗 RISC-V 上是 32 位，`2000*num` 到 2e11 溢出成负数 → 改 `int64_t` |
| 心率恒 200 | 自相关已给出 73/76/79，输出却永远是 200 | `hist[hn % 5]`，`hn` 封顶在 5 后取模恒为 0，5 格里 4 格永远停在启动初期的 200 → 写指针独立自增取模 |
| 单窗掉链子就清零 | 76 → 0 → 76 乱跳 | 投票遇到无效值直接返回 0 → 改为沿用上次中位数，连续 3 窗无效才归零 |

#### 最终算法链

```
原始 IR(200Hz) -> 3s 滑动均值去漂移 -> 20 点滑动平均(≈10Hz 低通)
   ├─ 自相关：lag 60~400 点，取第一个达到峰值 85% 的 lag，输出相关度
   └─ 峰值检测：门限 = 幅度/6，间隔中位数
两条路径偏差 ≤20% 取平均，否则信自相关；运动中（漂移>700 或幅度>1500）不给数
-> 5 窗中位数投票（带保持）-> 输出
```

#### 关键参数（都已实测标定）

| 参数 | 值 | 依据 |
| --- | --- | --- |
| 采样率 | 199 Hz | 日志每行尾部实测 |
| 增益 | `SPO2_CFG=0x0C`（2048nA） | DC 从 17400 升到 33000，摆幅 320→1500，并回读确认 |
| 指纹门限 | `ir_max > 6000` | 无手指 3700~3900，有手指 1.7 万~4.1 万 |
| 运动门限 | `漂移>700 或 幅度>1500` | 静息 160~450/420~970，挪动 983~1319/1747~1905 |
| 相关度门限 | ≥0.40 | 有效窗 0.45~0.95，噪声窗 ≤0.30 |

#### 遗留

- 血氧 93~100%，偶有 0（`spo2_valid=0`），未做单独标定，**只能当参考**；
- 心率上下浮动约 ±5 bpm（5 秒一窗 + 5 窗中位数），做手表 UI 时建议再串一个 3 点平均；
- **这颗 MAX30100 只输出 11 位有效数据**（低 5 位恒 0），所以 Maxim 官方算法在这块板上永久不可用，别再去调它。

## 9. 摔倒检测（2026-11-01 09:40，固件 `HY-SENSOR-12`）

### 9.1 判定链

**冲击 + 静止** 两个条件都满足才算，缺一不报：

| 阶段 | 判据 | 说明 |
| --- | --- | --- |
| 冲击 | 合加速度模长 ≥ **2.0g** | 走路/坐下/拍手都在 1.5g 内；实测落板 5.35g、手磕 2.29g |
| 回弹期 | 冲击后 **500ms** 不计 | 落地有回弹，这段不算「静止」 |
| 静止 | 之后 5 秒内模长峰峰 ≤ **300mg** | 实测静置时抖动仅 20~40mg，远低于门限 |
| 排除 | 1 秒峰峰 ≥ **600mg** | 磕碰后必然继续活动，用它排除 |
| 复报 | 每 5 秒一次 | 人躺着不动时告警不会自己消失 |
| 解除 | 检测到活动 | 起身即解除 |

### 9.2 硬件前提：量程必须改 ±8g

原来是 `ACCEL_CFG=0x00`（±2g, 16384 LSB/g），摔倒冲击 3~6g 会**直接削顶**，
削顶后所有冲击看起来都是 2g，摔倒和磕桌角分不开。
改成 `0x10`（**±8g, 4096 LSB/g**），代价只有分辨率 0.24mg。
同时把加速度采样从 50Hz 提到 **100Hz**（`HY_ACC_DIV 2→1`），冲击尖峰只有几十毫秒。

### 9.3 三个必须绕开的坑

**坑 1：冲击尖峰会把「活动度」顶爆**
第一版没做任何处理，冲击样本进入 1 秒活动窗，峰峰值直接 3~8g，
于是每次摔倒都在 1 秒后被自己判成「冲击后有活动」→ 100% 漏报。
处理：冲击发生、回弹期结束各重置一次活动窗，且**活动窗只统计 <2g 的样本**。

**坑 2：静止统计的初值含冲击峰**
`s_still_min/max` 用冲击那一刻的 4000+mg 初始化，5 秒窗峰峰值永远超门限，
真摔倒被判「未静止」。处理：回弹期结束时把静止统计重新起算。

**坑 3：告警行被 `Output illegal string! vsnprintf_s failed!` 吞掉**

症状很迷惑：`fall=疑似摔倒(1次)` 计数正常、复报也正常，**唯独告警那一行没出现**。
第一反应是「太长」，拆成三行后中间那行仍然丢——真正原因是**格式串写错**：

```c
printf("... 静止 %d.%01fs\r\n", ...);   /* 错：%01f 是浮点转换，实参是整数 */
printf("... 静止 %d.%01ds\r\n", ...);   /* 对 */
```

`%01f` 后面那个 `s` 只是普通字符，转换符是 `%f`。SDK 的 printf 去取 double 拿到垃圾，
拼出的字符串非法，于是整行丢弃。**同理：64 位实参必须转成 `int` 再配 `%d`**。

> 经验：看到 `fall=` 状态对了但文字没了，先查格式串，别怀疑长度。

### 9.4 实测（真机，`HY-SENSOR-13`）

```
[hy-fall] 冲击 2.63g，开始观察是否静止（5 秒）
[hy-sensor] acc ... | fall=观察(0次) | ...
[hy-fall] ===== 疑似摔倒 =====          ← 5.1 秒静止后，三行告警完整打印
[hy-fall] 冲击 2.63g 静止 5.1s
[hy-fall] 抖动 156mg 模长 991mg
[hy-sensor] acc ... | fall=疑似摔倒(1次) | ...
[hy-fall] 仍在静止，疑似摔倒持续 10 秒，请确认本人状态
```

另一轮更狠的落板（5.35g，前有失重）同样在 5 秒后告警。

被排除的反例（都是应有的行为）：

```
[hy-fall] 冲击 3.33g，开始观察是否静止（5 秒）
[hy-fall] 已排除：冲击后有活动（1 秒峰峰 1342mg）    ← 板子在手上被连续晃
[hy-fall] 已排除：未静止（5 秒内抖动 469mg > 300mg）  ← 磕碰后手还在动
```

离线 6 场景回放（100Hz 合成信号）也全部符合预期：
静置/走路不报；摔倒后不动 → 告警并复报；磕碰后走路、坐下打字、3 秒内爬起 → 全部排除。

**状态行新增 `pk=`**：每 500ms 窗口内的合加速度峰值，用来标定力度
（静置 1.00~1.06g，手磕 2.1~3.4g，15cm 落板 3.4~5.4g，砸桌 8~9g）。

### 9.5 已知边界

- **轻放桌上**（冲击 <2g）不会触发，这是设计如此；
- 摔倒后**马上被扶起**（5 秒内）不会报警——需要更短窗口可把 `FALL_STILL_MS` 调小；
- 手表戴在手腕上时，摘表动作（甩落）也可能触发，实测需再标定；
- 硬摔会让 **WEAR 排针瞬间接触不良**：本轮 5.35g 落地后 `ir_max` 从 4700 掉到 256，
  重新插紧即恢复——**摔检测测试后要检查 WEAR 是否还在位**。

## 10. 华为云 IoTDA 上云（HY-CLOUD-14）

### 10.1 为什么是手写 MQTT

SDK 里只有一个 `open_source/mqtt/paho.mqtt.c`，那是给 Linux/POSIX 用的，线程模型和
内存模型都不适合 LiteOS，编进来也起不来。所以按 IoTDA 的实际需要裁了一个
最小实现：CONNECT / CONNACK / PUBLISH / PINGREQ / PINGRESP / DISCONNECT，只做 QoS 0。

### 10.2 文件分工

| 文件 | 职责 |
|---|---|
| `hy_cloud_cfg.h` | 全部可配置参数（WiFi、三元组、域名、周期） |
| `hy_net.c/h` | WiFi STA 关联 + DHCP + 极简 SNTP 取时 |
| `hy_mqtt.c/h` | MQTT 3.1.1 客户端（lwip socket） |
| `hy_sha256.c/h` | SHA-256 / HMAC-SHA256，只给鉴权用，不拖 mbedtls |
| `hy_cloud.c/h` | 业务层：三元组、组 JSON、周期上报、摔倒补报、断线重连 |

上云任务优先级 **16**，低于传感器（20）和 LCD（24），WiFi 再忙也不抢采样。
`HY_CLOUD_ENABLE 0` 可以整体关掉。

### 10.3 华为云鉴权规则（踩坑点）

```
ClientId = {device_id}_0_{密码签名类型}_{时间戳}
          密码签名类型 1 = 平台校验时间戳（推荐）
          时间戳 = UTC 的 YYYYMMDDHH，注意只到「小时」
Username = {device_id}
Password = hex( HMAC-SHA256( key = 时间戳字符串, msg = 设备密钥 ) )
```

**两个致命细节**：

1. HMAC 的 **key 是时间戳、msg 是密钥**，和直觉相反；
2. 明文 1883 接入时平台**强制校验时间戳**（防重放），所以设备必须能拿到可信 UTC。
   WS63 没有 RTC 备份电池，每次上电都得重新 SNTP 一次。

### 10.4 控制台要做的事

1. 创建产品 → 选「MQTT」接入；
2. 「模型定义」导入 `D:\ws63\iotda_product_model.json`（服务 ID `Health`，8 个属性）；
3. 注册设备 → 认证方式选「密钥」→ 保存好 **设备 ID** 和 **设备密钥**（密钥只显示一次）；
4. 「总览 → 接入信息」抄下 **MQTT 接入地址**。

属性名必须是：`heart_rate` `spo2` `accel_x` `accel_y` `accel_z` `steps` `fall_state` `fall_count`。
名字对不上平台会拒绝，串口里会打出 `[hy-mqtt] 平台下行 ...` 的原始报文。

### 10.5 烧之前先自检

```
python D:\ws63\hw_iotda_probe.py <接入域名> <设备ID> <设备密钥> Health
```

纯标准库，依次验证 TCP → CONNACK → 属性上报。三元组错会直接告诉你是哪一关。

### 10.6 串口日志判读

```

[hy-net] WiFi 协议栈就绪
```

### 10.7 DHCP/socket 全部失败的真正根因（HY-CLOUD-18 修复）

**现象**：WiFi 能扫到 AP、能关联、四次握手全过，但
`dhcp_start` 一直返回 **-1**，同时 `socket()` 返回 **-1 / errno=105(ENOBUFS)**。

**排除过程**（都被证伪，别再走这些弯路）：

| 假设 | 反证 |
|---|---|
| 网卡 MTU=0 | 打印 `mtu=1500 up=1 link=1 hwlen=6`，本来就是 1500 |
| DHCP 起太早（网卡没 up） | 等 link up + 重试 5 次，仍 -1 |
| 信号量耗尽（`LOSCFG_BASE_IPC_SEM_LIMIT=32`） | 真实配置是 `LWIP_TCPIP_CORE_LOCKING=1`，netifapi 不建信号量；改成 128 也无变化 |
| lwip 堆不够 | `MEM_LIBC_MALLOC=1`，`mem_malloc` 正常 |

**根因**：`tcpip_init()` 在整个固件里**只有一个调用点**——`wifi_host_task` 内，
且**只有 `uapi_wifi_init()` 返回 0 才往下执行**。这条链一断，`tcpip_init → lwip_init → memp_init`
就完全没跑，所有内存池都是空的。表现就是：

- `mem_malloc` 成功（走 libc，不依赖 memp）
- `pbuf_pool` / `udp_new` / `netconn` / `socket` **全部失败**
- `dhcp_start` 首步 `udp_new()` 失败 → 返回 `ERR_MEM`(-1)

WiFi 扫描/关联/握手走的是驱动层 WAL/HAL，压根不过 lwip，所以"网络看起来是好的"。

**修法**：在 `hy_net.c` 里做 7 项分配探测（`mem_malloc` / `pbuf_ram` / `pbuf_pool` /
`udp_new` / `tcp_new` / `netconn` / `socket`），成功项 <3 就补一次
`tcpip_init(NULL, NULL)`（自带完成标志，重复调用是空操作，安全），然后再测一遍。

**验证**：补初始化后 A 组即全绿，`dhcp_start ret=0`，拿到 IP，SNTP 取到时间
`2026110103`，MQTT CONNACK 0x00，属性上报成功。

### 10.8 设备密钥与"连接密钥"文件的区别

控制台下载的 `DEVICES-CONNECT-KEY-*.txt` 里的 `password` 是
`HMAC-SHA256(设备密钥, 时间戳)` 的**结果**，不是设备密钥本身，且**每小时变一次**，
不能直接写进固件。固件里必须写注册设备时给的**原始设备密钥**。

反证方法（已实测）：故意把密钥改成 32 个 0，CONNACK 立刻返回 **0x04**，
说明平台确实校验密码；换回真密钥返回 **0x00**。所以只要 0x00 就证明密钥无误。

### 10.9 控制台"在线但没数据"——服务 ID 对不上（HY-CLOUD-19 修复）

**现象**：设备在线，MQTT 连续 20 分钟不断线，串口每 10 秒打印"上报成功"，但控制台
物模型数据一直是空的。

**根因**：固件里 `service_id` 写的是 `Health`，而这个产品在控制台里建的
**服务 ID 是数字 `11`**。平台收到报文后找不到对应服务，**静默丢弃**——
属性上报是单向的，平台不会断开连接、也不会回错误，所以"在线"和"没数据"能同时成立。

**定位方法（不用烧录、不用反复试）**：用设备影子反查。发一条属性上报，
再请求 `$oc/devices/{id}/sys/shadow/get/request_id=xxx`，看 `reported` 有没有更新。
影子是判断"平台到底收没收到"最快的证据来源：

- 影子不更新 → 报文被拒（服务 ID / 属性名 / 类型不对）
- 影子更新了 → 平台收到了，问题在展示侧

暴力试探服务 ID 的技巧：一条连接里连发多个候选 `service_id`（每个配不同数值），
再查影子，哪个值进去了哪个就是对的。

**结论**：`service_id` 必须与控制台「模型定义」里那个服务的**服务 ID 逐字一致**，
大小写都算。已经改成 `"11"`。

**旁证**：控制台下载的 `DEVICES-CONNECT-KEY-*.txt` 里的 `password` 是
`HMAC-SHA256(key=时间戳, msg=设备密钥)`——注意 **key 是时间戳、消息才是密钥**，
和常见写法相反，按这个公式算出来的值和文件里的完全相同（实测逐字节吻合）。
