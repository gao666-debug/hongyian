# WS63 星闪板 上云接入与运维说明

> 版本：v1.0（2026-11-01）
> 适用：`920_home_cloud` 固件 + `eldercare-backend`（多设备版）
> 本文档记录的是**实际跑通**的配置，以及踩过的坑。卡住时优先看第 5 节「排查手册」。

---

## 1. 架构与数据流

```
WS63 传感器节点                      华为云 IoTDA                  阿里云服务器
┌──────────────┐   Wi-Fi 2.4G   ┌──────────────┐   AMQP    ┌──────────────────┐
│ 光敏 ADC5     │ ────────────→ │ 设备鉴权      │ ────────→ │ eldercare-amqp    │
│ 烟雾 ADC0     │   MQTT 1883   │ 物模型校验    │           │ eldercare-api     │
│ 人体 GPIO14   │               │ 数据转发规则  │           │ SQLite            │
│ 门磁 GPIO6    │               │ 设备影子      │           │ WebSocket → App   │
└──────────────┘               └──────────────┘           └──────────────────┘
```

两条上报通路，用途不同，**缺一不可**：

| Topic | 用途 | 平台侧表现 |
| --- | --- | --- |
| `$oc/devices/{id}/sys/properties/report` | 控制台展示、答辩演示 | 刷新「设备影子 / 最新上报数据」 |
| `$oc/devices/{id}/sys/messages/up` | 自建后端入库 | 触发 `device.message` 转发 → 后端 |

> ⚠️ 后端**只接受** `device.message` 转发（`resource=='device.message' && event=='report'`）。
> 属性上报转发到后端时的 `resource` 是 `device.property`，会被直接 422 拒掉。
> 所以**只发属性上报是不够的**，必须同时发自定义消息。

## 2. 华为云侧配置

### 2.1 产品与物模型

| 项 | 值 | 备注 |
| --- | --- | --- |
| 产品名称 | `33` | 随意 |
| 产品 ID | `6ae6af2518855b39c55ba694` | 设备ID 的前缀就是它 |
| 协议类型 | MQTT | |
| **数据格式** | **JSON** | 选成「二进制透传」会导致属性永远不落库，且**创建后不可改** |
| 服务 ID | **`11`** | ⚠️ 必须与固件 `cfg.h` 的 `CFG_IOTDA_SERVICE_ID` 完全一致 |

属性（服务 `11` 下）：

| 属性名 | 类型 | 说明 |
| --- | --- | --- |
| `light` | decimal | 光敏 ADC 电压 mV（0~3300） |
| `smoke` | decimal | 烟雾 ADC 电压 mV（0~3300） |
| `body` | int | 人体感应 1=有人 0=无人 |
| `door` | enum | `OPEN` / `CLOSED` |
| `temp` | decimal | 预留（AHT20，未启用） |
| `humi` | decimal | 预留。**当前建成 int，将来上报 60.5 这类小数会被拒，建议改 decimal** |

### 2.2 注册设备

- 节点 ID：`1234`
- 设备 ID：`demo-environment`
- 注册后控制台会下载 `DEVICES-CONNECT-KEY-*.txt`，里面的 `clientId` / `password` 直接填进固件 `cfg.h`

**关于 clientId 的时间戳**：格式 `{设备ID}_0_0_YYYYMMDDHH`，其中时间是 **UTC，不是本地时间**。
实测本地 11:32 导出的凭据尾号是 `2026110103`（UTC 03 点）。
实测结论：**平台不按小时严格校验时间戳**，这组固定凭据可长期使用，不必每次都重新生成。

### 2.3 数据转发规则（最容易漏的一步）

规则名：`ZhianSafetyDeviceReports`，转发目标：AMQP 消息队列。

**数据过滤语句必须包含所有设备**，原始配置写死了旧设备，导致新设备数据永远到不了后端：

```sql
SELECT *
FROM DEVICE_MESSAGE_REPORT
WHERE notify_data.header.device_id = 'demo-device'
   OR notify_data.header.device_id = 'demo-environment'
```

> 必须用 `OR`，**不要用 `IN`** —— 这套转发 SQL 只支持很小的子集。
> 更省事的写法是去掉整个 `WHERE`（以后加设备不用再改），后端已用 `DEVICE_ID` 白名单做二次校验。
>
> ⚠️ 改完 SQL 后回到页面第 3 步确认规则状态是**「已启动」**，有时会变成未启动。

## 3. 固件

### 3.1 目录与文件职责

```
src/application/samples/demo/920_home_cloud/
├── cfg.h        所有配置（WiFi / 三元组 / 服务ID / 引脚 / 上报节奏）
├── sensors.c/h  四路采集 + 开门提示灯
├── net.c/h      Wi-Fi STA 连接 + SNTP 校时
├── iotda.c/h    MQTT 连接与上报
└── main.c       任务编排（只管流程，不放业务细节）
```

另有 `910_net_time`（最小联网+校时示例），排查网络问题时先烧它，能快速区分是网络还是业务问题。

### 3.2 关键配置项（`cfg.h`）

| 宏 | 当前值 | 说明 |
| --- | --- | --- |
| `CFG_WIFI_SSID` / `CFG_WIFI_PASS` | `lumine` / 手机热点 | **只支持 2.4GHz** |
| `CFG_IOTDA_HOST` | `YOUR_INSTANCE.st1.iotda-device.cn-east-3.myhuaweicloud.com` | 控制台「总览 → 接入信息」 |
| `CFG_IOTDA_PORT` | 1883 | 明文；8883 需配 TLS |
| `CFG_IOTDA_SERVICE_ID` | `11` | 必须与物模型一致 |
| `CFG_REPORT_PERIOD_MS` | 10000 | 定时上报间隔 |
| `CFG_LAMP_HOLD_MS` | 15000 | 关门后提示灯延时熄灭 |

### 3.3 上报策略

- **定时上报**：每 10 秒一次全量四路快照
- **事件立即上报**：门磁开/关、PIR 有人/无人变化时立刻补发一条（最小间隔 1 秒防抖）
- 每次上报都发**属性 + 消息**两条 Topic

### 3.4 编译

```bash
/d/ws63_dev/build.sh          # 增量
/d/ws63_dev/build.sh clean    # 全量（15~25 分钟）
```

**必须遵守的三条**：

1. 编译参数必须带 `-nhso`（HSO 符号索引在本机会永久卡死，与固件无关）
2. **输出绝对不要接管道**（`| tee` / `| tail`）。全量重编时输出量大，会把 `cmd.exe → ninja → gcc` 整条链路塞死，表现为只剩一个 cmd 空转、`.obj` 不再增长
3. **切换 demo 后必须先删 `output/ws63/acore/ws63-liteos-app/application/samples/libsamples.a`**，否则旧 demo 的 .obj 会被复用，出现「改了代码没生效」

### 3.5 烧录

```bash
cd /d/ws63_dev/tools/BurnToolCmd && ./BurnToolCmd.exe --burn
```

- 工具每轮只监听约 30 秒，**按 RST 要卡在这个窗口内**；错过就多按几次（间隔 20 秒）
- **崩溃循环时按 RST 是抢不到下载窗口的**（软复位直接跳 app）。唯一办法：
  **按住 RST → 启动烧录工具 → 松开 RST**
- 换 USB 口会导致 COM 号变化（COM5 ↔ COM6），要同步改 `config/burn.config` 的 `serialPort`

## 4. 后端（多设备改造）

### 4.1 改了什么

原版是**单设备**设计，两处独立的单设备判断，**两处都要改**：

| 文件 | 位置 | 原逻辑 | 改后 |
| --- | --- | --- | --- |
| `backend/settings.py` | 新增 | — | `device_ids` 属性（逗号分隔）+ `has_device()` |
| `backend/app.py` | `check_device()` | `device != settings.device_id` | `not settings.has_device(device)` |
| `backend/app.py` | 登录返回 | `[settings.device_id]` | `settings.device_ids` |
| `backend/app.py` | 命令查询 / WebSocket / mock 种子 / 抓拍联动 | 单值 | 全部改为多设备 |
| `backend/app.py` | `Health` 模型 | 无传感器字段 | 新增可选 `light/smoke/body/door` |
| **`consume_cloud.py`** | AMQP 消费者 | `device != settings.device_id` | `not settings.has_device(device)` |

> ⚠️ `consume_cloud.py` 那份过滤**极易漏掉**。它不在 `backend/` 目录下，逻辑与 `app.py` 重复。
> 漏掉它的表现是：云端消息已经到服务器了，但被消费者在入口静默丢弃（`REJECTED` + `settle`，
> 连 dead-letter 都不留），日志里看不出任何异常。

### 4.2 环境变量

```bash
DEVICE_ID=demo-device,demo-environment
```

单个值仍然完全兼容旧行为。

### 4.3 部署

```bash
scp -i <key> backend/app.py backend/settings.py consume_cloud.py deploy@SERVER_IP:/tmp/_newupd/
ssh -i <key> deploy@SERVER_IP 'bash -s' < deploy_update.sh
```

**部署前必做**：先把服务器上的当前版本下载下来 `diff` 一遍，确认只有自己的改动，
避免覆盖掉服务器上后来做的修改。

**部署后必做**：重启两个服务才生效

```bash
systemctl --user restart eldercare-api eldercare-amqp
```

**回滚**：备份文件名带时间戳（如 `app.py.bak-20261101172930`），改回原名重启即可。

## 5. 排查手册

> 这套顺序是实际趟出来的，从"确定是哪一段坏了"开始，逐层往里收。

### 第 1 步：板子在发吗

串口 115200，看有没有：

```
[IOTDA] report light=492 smoke=154 body=1 door=OPEN (prop=0 msg=0)
```

`prop=0 msg=0` 表示两条 Topic 都发送成功。如果 `connect FAILED rc=N`：

| rc | 含义 |
| --- | --- |
| 2 | clientId 非法（格式或时间戳不对） |
| 4 | 账号密码错误（多为 HMAC/时间戳问题） |
| 5 | 未授权 |

### 第 2 步：平台收到了吗

IoTDA 控制台 → 设备 → **消息跟踪** → 启动 → 等 30 秒。

这是**唯一**能看到平台判定的地方。常见结果：

| 业务步骤 | 状态 | 含义 |
| --- | --- | --- |
| 平台收到设备的属性上报 | 成功 | 报文格式没问题 |
| **属性上报设备影子刷新** | **失败** + `service ID ... is not defined` | 固件里的服务 ID 与物模型不符 |
| 平台收到设备的消息上报 | 成功 | 自定义消息这条路通了 |

> 设备**无法订阅** `.../sys/properties/report/response`（SUBACK 返回 `0x80`），
> 用 PC 上的标准 paho 客户端试也一样。所以别指望从设备侧拿回执，直接看消息跟踪。

### 第 3 步：到服务器了吗

```bash
journalctl --user -u eldercare-amqp -n 20 --no-pager
```

看到 `[cloud-consumer] Device message persisted` 说明消费者收到了并转给了后端。
**完全没有** → 云端转发规则没覆盖这台设备（查 2.3）。

### 第 4 步：入库了吗（最关键）

```bash
sqlite3 /home/deploy/app/.local/backend.sqlite3 \
  "select device,count(*) from inbox group by device;"
```

**日志说 persisted 但条数不涨**，说明消息被后端当成重复丢弃了：

- `id` 字段每条必须唯一（后端 `INSERT OR IGNORE INTO inbox`）
- `boot_id` 必须每次开机不同且递增（后端用 `(boot_id, up)` 判新旧，否则报
  `older health report` 静默拒绝，表现为 inbox 会涨但 `documents` 里的影子不更新）

### 第 5 步：区分"应用层"和"云端转发"

直接往服务器本地接口注入一条测试消息，绕过云端：

```bash
ssh deploy@SERVER_IP
cd /home/deploy/app && .venv/bin/python - <<'PY'
import json,os,time,requests
from dotenv import load_dotenv
load_dotenv("/home/deploy/app/.env",override=False)
dev="demo-environment"
inner={"name":"device_health","id":"probe-%d"%int(time.time()),"content":{
 "fw":"probe","boot_id":1,"epoch":int(time.time()),"up":1,
 "env_valid":1,"imu_valid":0,"door_enabled":1,"wireless_btn_enabled":0,
 "mute":0,"tls":False,"light":902,"smoke":155,"body":1,"door":"OPEN"}}
p={"resource":"device.message","event":"report",
   "notify_data":{"header":{"device_id":dev},"body":{"content":json.dumps(inner)}}}
r=requests.post("http://127.0.0.1:8000/api/v1/iotda/notifications",json=p,
                headers={"X-Webhook-Token":os.getenv("WEBHOOK_TOKEN","")},timeout=10)
print(r.status_code, r.text[:200])
PY
```

返回 `200 / accepted:true` → 应用层没问题，找云端；返回 4xx → 应用层的问题，看返回体里的 message。

### 差分测试技巧

排查"哪个参数不对"时，一条条试效率极低。更快的做法是**一次发多条、用不同的属性值标记**，
例如 `light=881/882/883` 分别对应三个候选参数，看最终落库的是哪个值就知道哪个参数对。
这个办法当初就是靠它把服务 ID 锁定成 `11` 的。

## 6. 已知限制

| 项 | 现状 | 影响 |
| --- | --- | --- |
| 传输加密 | 1883 明文 | 演示可用，正式上线建议升 8883（mqtt 组件已编 mbedtls） |
| 时间源 | 无 RTC，靠 SNTP 校时后累加 tick | 长时间运行会有累积漂移；重启后重新校时 |
| 设备密钥 | 明文写在 `cfg.h` | 不要提交到公开仓库；泄露后在控制台「重置密钥」 |
| `humi` 类型 | 物模型建成 int | 将来上报小数会被拒，需改 decimal |
| 温湿度 | AHT20 未接入 | `temp`/`humi` 属性目前不上报 |
| 断线重连 | 连续 3 次上报失败后重建 MQTT 客户端 | Wi-Fi 重连依赖 SDK 自身行为，未做主动重扫 |
