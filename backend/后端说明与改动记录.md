# 后端 · 源码说明与改动记录

> 线上版本：**API 1.4.0**
> 服务器：`deploy@SERVER_IP`（阿里云轻量，上海，2C2G / Ubuntu 22.04）
> 技术栈：FastAPI + SQLite + 华为云 IoTDA SDK + qpid-proton(AMQP)

## 一、文件职责

| 文件 | 职责 |
|---|---|
| `backend/app.py` | 主应用：所有 HTTP 路由、WebSocket 推送、设备消息入库 |
| `backend/store.py` | SQLite 存储层（documents 表复用，零迁移） |
| `backend/cloud.py` | 华为云 IoTDA 客户端（取影子、下发命令） |
| `backend/settings.py` | 配置加载（`.env` → Settings） |
| `backend/medicine.py` | 三次服药提醒的模型与 mock 逻辑 |
| `backend/watch.py` | **手表属性归一化**（1.4.0 新增） |
| `consume_cloud.py` | AMQP 消费者：从华为云队列取消息 → 转给本地 API |
| `run.py` | 启动入口（uvicorn） |
| `requirements.txt` | 依赖 |
| `.env.example` | 配置模板（**本包只有模板，无真实值**） |

## 二、启动

```bash
cd eldercare-backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env      # 然后按下面第三节填
chmod 600 .env

python tools_init.py      # 首次：初始化账号密码与 webhook token
python run.py             # 启动 API（默认 127.0.0.1:8000）

python consume_cloud.py   # 另开一个进程：AMQP 消费者
```

生产环境这两个进程由 systemd 用户服务托管：`eldercare-api.service`、`eldercare-amqp.service`。

> ⚠️ 这两个服务跑在 **deploy 用户**的 systemd 会话下。
> 用 root 执行 `systemctl --user is-active` 会**误报 inactive**，必须用 deploy 账号查。

## 三、配置项（`.env`）

| 变量 | 说明 |
|---|---|
| `BACKEND_MODE` | `live`（真实设备）/ `mock`（本地假数据） |
| `DEVICE_ID` | 设备白名单，**逗号分隔**多台。当前：主监护板,环境节点 |
| `WATCH_DEVICE_ID` | 手表设备 ID（单独配，不在 `DEVICE_ID` 里） |
| `WATCH_SERVICE_ID` | 手表物模型服务 ID（默认 `11`） |
| `APP_USERNAME` / `APP_PASSWORD` | App 登录账号 |
| `WEBHOOK_TOKEN` | IoTDA 转发回调的鉴权头（≥24 字符） |
| `IOTDA_ENDPOINT` / `IOTDA_REGION` / `IOTDA_PROJECT_ID` | 应用侧 AK/SK 调用 |
| `HUAWEICLOUD_SDK_AK` / `SK` | 华为云应用凭据 |
| `AMQP_HOST` / `AMQP_ACCESS_KEY` / `AMQP_ACCESS_CODE` / `AMQP_QUEUE` | AMQP 消费者凭据 |
| `DATABASE_PATH` | SQLite 路径，默认 `.local/backend.sqlite3` |

> ⚠️ **AMQP 接入凭证会过期，且过期后已建立的连接不会被踢**——
> 平时看不出异常，一旦重启服务就连不上（表现为 `Transport failure; reconnecting` 死循环）。
> 2026-11-02 踩过这个坑。重启后务必确认日志出现 `Device message persisted`。

## 五、改动记录（相对队友最初的 1.2.0）

### 1.2.0 → 中间版（2026-11-01，**未升版本号**）

多设备适配，改动点：

- `settings.py`：新增 `device_ids` 属性（`DEVICE_ID` 逗号分隔）、`has_device()`
- `app.py`：`check_device()` 改用 `has_device()`；登录返回 `device_ids` 列表；
  mock 影子按设备逐个初始化
- `Health` 模型新增 4 个可选字段：`light` / `smoke` / `body` / `door`（给 WS63 环境节点用）

> ⚠️ 这次改动**没有升版本号**，所以查 `/healthz` 或 version 会误判线上没变。判断线上有没有改，要核对 `app.py` 的 md5。

### 1.3.0（2026-10-24）· 视觉抓拍 + AMQP 死信

| 改动 | 说明 |
|---|---|
| 新增 6 个抓拍路由 | 复用 `documents` 表（kind=`capture_request`/`capture`），零迁移 |
| 图片落盘 | `.local/captures/{capture_id}.jpg`，DB 只存元数据 |
| 安全加固 | 上传校验 JPEG 魔数 `FF D8`；取图校验路径不能越出 `CAPTURE_DIR` |
| `consume_cloud.py` 死信 | 收到 422 时先把原始报文写 `.local/dead-letter/YYYYMMDD.jsonl` 再出队，不再静默丢数据 |
| nginx | `client_max_body_size 8M`（原来默认 1M，抓拍图会被 413 挡掉） |
| 报警联动开关 | `CAPTURE_ALARM_CODES`（默认空=关闭，因 `alarm.code` 1~5 的语义当时未确认） |

### 1.3.1（2026-11-02）· 修复 shadow 服务 ID 写死

**问题**：`cloud.py` 里 `shadow()` 只挑 `service_id == 'HomeSafety'` 的服务，
而 WS63 环境节点的属性挂在服务 `11` 下 → 新设备 `/shadow` 返回 `properties: {}`，
App 读影子会整屏空白。

**修复**：

```python
# 优先 HomeSafety（主监护板行为逐字节不变）
preferred = next((s for s in services
                  if s.get('service_id') == 'HomeSafety' and reported_props(s)), None)
if preferred is not None:
    chosen, properties = preferred, dict(reported_props(preferred))
    stamp = (preferred.get('reported') or {}).get('event_time')   # 时间与属性同源
else:
    # 没有 HomeSafety 时合并所有服务的属性（新设备走这条）
    ...
```

`updated_at` 与属性必须**取自同一个服务**，否则会出现「旧属性配新时间」。

### 1.4.0（2026-11-02）· 合并手表链路

| 改动 | 说明 |
|---|---|
| 新增 `backend/watch.py` | 手表属性归一化：范围校验、mg→g 换算、派生 `motion_mg`/`dynamic_mg`/`posture`/`hr_measuring`/`fall_active` |
| `store.py` 新增 `watch_hour()` | 按小时滚桶（10 秒一条，一天 8640 条不落全量） |
| `settings.py` | 新增 `watch_device_id` / `watch_service_id` / `allowed_device_ids` / `primary_device` / `is_watch()` |
| `app.py` | `WatchService`/`WatchReport` 模型、`ingest_watch()`、3 个查询接口、`/mock/watch` |
| `notifications` | 支持 `device.property`（手表走属性上报） |
| `consume_cloud.py` | `notification()` 接受 `device.property` |

**三处刻意与队友原版不同**（都是因为本项目的多设备改造）：

1. **手表数据挂 `primary_device`（= `device_ids[0]`）**，不是 `settings.device_id`。
   后者是多设备逗号串，直接当 device 用会写出 `"A,B"` 这种脏键。
2. **白名单拆两层**：`device_ids`（App 可见 = 主板 + 环境节点）/ `allowed_device_ids`（+ 手表，供入库校验）。
   这样登录仍返回 2 台设备，前端不用为手表新增一张卡片。
3. **非手表设备的属性上报返回 200-ignored**，未知设备仍 404。
   环境节点每 10 秒也发属性上报、服务 ID 同为 `11`，若一律送进 `ingest_watch`
   会因「无手表属性」被 422 → 每 10 秒一条死信。

## 七、部署与回滚

单测不过自动回滚。

回滚点目录：`/home/deploy/app/.local/code-backup/YYYYMMDD-HHMMSS/`

> ⚠️ 备份必须包含 `backend/`、`tests/`、`consume_cloud.py`——
> 早期脚本漏了 `tests/`，导致改了测试文件也回滚不了。
