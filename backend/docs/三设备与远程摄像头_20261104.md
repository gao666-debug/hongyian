# 颐鸿安三设备与远程摄像头（2026-11-04）

## 使用目标

一次部署、一次摄像头配置与烧录。之后 ESP32-CAM 通电连接可上网 Wi-Fi 进入待机，收到 App 观看请求后才上传，手机登录家庭账号打开画面；不依赖家里电脑，不向互联网开放摄像头本身的端口。保留同 Wi-Fi 直连。更换热点密码、服务器地址、证书或撤销上传凭据后需要重新配置摄像头，不能保证永远不重配。

## 数据与账号

- 登录返回 `device_ids` 和带 `kind` 的 `devices`；家庭接口 `/api/v1/household` 返回设备、属性和归一化手表快照。
- App 按唯一 `kind=gateway` 选择主机，不按数组下标。环境仅接收 nearlink/environment，wearable 不混入环境。旧数据库中误标为 nearlink 的已配置手表会修正为 wearable，不移动家庭归属。
- 手表原始属性通过手表 `/shadow`；归一化结果、小时与跌倒记录继续通过主机 `/watch`。心率 0、`hr_measuring=false` 显示未测到。
- 摄像头绑定现有 gateway，不冒充第四台 IoTDA 设备，不需要额外 IoTDA 产品。摄像头上传专用凭据只能发图，不能登录或查询家庭。owner 才能签发、轮换、撤销；viewer 可以观看和本地保存，不能改绑定。
- 保留已有家庭成员机制。这里没有新增公共注册、家庭自助开户或复杂多手表关联界面；服务器维护者仍负责初始家庭及设备绑定。

## 接口（均带 `/api/v1`）

| 方法与路径 | 用途与权限 |
|---|---|
| POST `/devices/{gateway}/camera/provision` | owner 签发一次性返回的 `camera_token`；重签使旧令牌失效 |
| DELETE `/devices/{gateway}/camera` | owner 撤销绑定和缓存 |
| POST `/devices/{gateway}/camera/frame` | 摄像头 `X-Camera-Token`；body 原始 JPEG，Content-Type image/jpeg |
| GET `/devices/{gateway}/camera` | 家庭 Bearer 登录；configured/online/received_at/bytes |
| GET `/devices/{gateway}/camera/frame` | 家庭 Bearer 登录；最新 JPEG 二进制 |
| GET `/devices/{gateway}/camera/stream` | 家庭 Bearer 登录；multipart MJPEG，boundary=frame |

单帧最大 512 KiB；帧 SOI/EOI 检查，App 负责解码；上传最多约 5 次/秒，固件目标上限约 2 次/秒，实际受采集、HTTPS 和带宽影响。15 秒无新图即离线，旧图接口返回 503，App 自动重试。在线流每 0.1 秒检查会话/家庭权限，退出账号或权限撤销后结束；每台摄像头最多 4 路观看。无匿名观看、无密码放 URL。

服务器只留每台摄像头最新一帧于内存，覆盖旧帧；进程重启后等待新图，设备绑定令牌哈希保存在原 SQLite 中。没有自动存全天录像、云端录像或无限图片历史。App 支持保存 JPG 与最长 60 秒无声 AVI，仍需用户手动导出。这样不增加磁盘无限增长的问题。**必须使用单个 API 进程/单 worker**，多 worker 需要额外共享帧服务，本版未实现。

## 服务器维护者一次性部署

1. 备份现有代码与数据库，保留 `.env`、SQLite、captures。更新 backend 源码，安装 requirements.txt（摄像头不新增 Python 依赖）。
2. API 使用原 127.0.0.1:8000，单进程。现有 `eldercare-api.service` 保持启动命令并设 Restart=on-failure；模板见 deploy。`systemctl --user daemon-reload`，`systemctl --user restart eldercare-api`。继续运行原 AMQP 消费者；勿在本机另起消费者分流。
3. nginx 现有 HTTPS server 内合入 `deploy/nginx-camera-location.conf`，由有权限维护者执行 `nginx -t` 再 reload。TLS 证书必须与 App 和摄像头信任的证书一致；自签 IP SAN 证书就用该 IP 地址，不改域名。禁止为了上线关闭证书校验。
4. 检查 `/healthz` 200，匿名 `/api/v1/household` 401，家庭账号取 household 200、三设备 kind 正确，未配置 camera 的 configured=false。已有业务路径代理不变。
5. 开机自启沿用 systemd 用户服务。服务器管理员需启用 deploy 用户 linger，才能在无人 SSH 登录时开机运行；账号无权限时交由管理员处理。

## 摄像头一次性配置

服务器新接口上线后，在本机后端目录运行（服务器地址用实际 HTTPS 地址）：

```bash
./.venv/bin/python tools_camera_provision.py \
  --server https://backend.example.com:8443 \
  --ca /path/to/trusted-public.crt \
  --username guardian \
  --output ../esp32cam/HomeSafetyCamera/cloud_private.h
```

终端交互输入管理员密码，不通过命令行传密码。脚本校验服务器证书、登录、按 kind 找主机、签发摄像头令牌、写权限 600 的私有头文件，最后退出登录。只在首次或主动轮换时运行，**不要每次启动都重签**。`cloud_private.h` 不发 GitHub、微信或交付包。原 `secrets.h` 继续保存 Wi-Fi 和本地摄像头账号。

随后 `cd ../esp32cam && bash scripts/build.sh`，按 ESP32-CAM 原方式烧录。固件 v0.3.1 校时后 HTTPS 上传，校验服务器证书，失败指数退避 1~30 秒，网络恢复自动重连；TLS 期间释放采集锁，本地接口保持可用。供电仍用摄像头独立 USB，不从通晓主板 3.3V 取电。

默认未提供 cloud_private.h 时远程上传关闭，仍能本地观看；因此旧固件或未配置的编译镜像不会自行获得远程能力。修改配置后必须重新编译再烧录。

## App

App 1.9.1 增加远程观看/同网直连切换并保存选择。现有开发证书和服务器公开证书合并为本地信任包，不靠硬编码服务器 IP 选择证书；没有关闭 TLS 主机名验证。远程模式从当前登录后端及已授权主机自动取地址，无需再输摄像头 IP；同网直连保留发现与地址配置。流畅模式是连续 JPEG 转发，省流模式每次取图后等待 1.5 秒，实际周期还含请求耗时。省流模式降低手机侧取图频率；退出页面或切后台释放观看请求，最后一个观众离开后停止远程取帧与上传。录像需先导出。

## 验收边界

本地接口与权限测试、App/固件编译通过后，仍需真实服务器部署、新令牌配置、摄像头烧录、4G/5G 观看验证才能宣称远程上线。至少验证：两手机独立账号观看、异家庭 404、viewer 不能重签、断电 15 秒离线、复电自动恢复、服务器重启自动恢复、证书/令牌错误不上传，以及 10 分钟温升/丢帧/内存。持续视频会消耗公网带宽，不能从 2 fps 目标推断已达到实测帧率。

## 按需观看（1.5.1 / App 1.9.1 / 摄像头 0.3.1）

- App 先 POST `/devices/{gateway}/camera/viewing`，取得 view_id；每 6 秒 PUT `/camera/viewing/{view_id}` 续期。每个手机会话独立，最多 4 个。
- 页面退出、停止、切后台时 DELETE `/camera/viewing/{view_id}`。另一个手机仍在看时保持上传；不能续期/关闭其他手机的观看请求。
- 异常退出或断网不再续期，20 秒后过期。服务端不再接受无人观看的上传（409）；上传途中最后一个观看请求结束也拒绝该帧。最后一个请求结束后清除最新帧缓存。
- 摄像头用专用 X-Camera-Token GET `/camera/demand`。响应头 X-Camera-Active 为 1 才取帧上传，为 0 则待机。待机每 5 秒查一次小型控制请求，观看中每 2 秒检查停传；控制失败即暂停并退避。
- 正常退出通常在下次控制检查（约 2 秒加网络耗时）停传；异常退出约 20 秒加检查/网络耗时停止。首次打开可能等待 0~5 秒加连接、采集时间；并非瞬间唤醒。
- 不看时停止的是远程取帧和图片上传，设备仍通电联网、传感器仍上电，不是深度睡眠或物理断电。本地直连仍可单独使用。待机有少量控制流量，不是零流量。
- 唤醒后丢弃驱动的旧缓冲，避免把待机前画面当新图。服务器重启不会继承观看请求，App 会自动重建；凭据仍有效。新旧三端必须一起更新，否则旧固件可能忽略 demand，新 App 可能找不到观看接口。
